Clear this repo's issue backlog autonomously, one batch at a time, until CENSUS below shows no issue left in a category this loop is responsible for. An empty `bd ready` list is never that proof. Never ask the user anything; when a choice arises take your recommended option and record it.

A batch is 1..N sibling issues sized against a complexity budget. One batch = one plan = one branch = one PR = one merge.

This procedure is the outer loop and shipping authority. For every batch, read the available `compound-engineering:lfg` skill and drive its current stages through the documented `ce-plan`, `ce-work`, review, browser-test, ship, and babysit seams. Do not invoke LFG as an indivisible child. Resolve every named child skill against the host's available-skills list and use host-native invocation; never guess slash or dollar syntax. Never bypass a child skill's applicable gates.

Why each rule exists, and the incidents behind it, is in this skill's `references/rationale.md` (not LFG's `references/`), keyed by section heading. It adds no rule; this file is complete without it. Steps are cited `I<n>` for the numbered ITERATION steps and `P<n>` for the numbered PIPELINE steps inside I5; where an older sentence says a bare `step N`, read it the same way: a PIPELINE step inside the PIPELINE list, an ITERATION step elsewhere, and "the blocked path in step 7" always means I7.

Resolve from the repo, report once, then start. Stop if a REQUIRED item won't resolve.

Unknown eligibility is `on` until disproved, never silent local fallback. Re-probe each current trunk SHA and each batch; CI unavailability is expected and pre-authorized, so never ask the user to fix billing.

A 403 is unprotected only when the response exactly says branch protection requires a paid plan or public repository; any other 403 is an authorization failure and stops. Do not flatten a conditional gate into one command or omit it. Child verification, post-merge verification, and the final report use this same gate set.

Every gate, test, build, or app command this loop runs is launched non-interactively (`CI=1`, watch and UI modes off), inside its own process group, and under a hard deadline `<gate-timeout>`, which is 20m unless the repository's CLAUDE.md, AGENTS.md, CONTRIBUTING.md, or README states a gate timeout, read at the gated commit as the quality gate set is, and then that value replaces it: `perl -e 'setpgrp(0,0); exec @ARGV' -- timeout -k 30s <gate-timeout> <command>`. `timeout` is `gtimeout` from Homebrew coreutils on macOS; where neither exists, keep the process group and enforce the deadline by killing that group. Export `BACKLOG_LOOP_RUN=<run-id>` into the host session environment right after choosing `<run-id>` and before any child skill runs, so every command a child launches -- `ce-work` tests, the `ce-test-browser` dev server, `ce-babysit-pr`, `ce-debug` -- carries the token a REAP or a dead-run sweep finds it by. Every child brief restates the hygiene rules in one sentence: run every gate, test, build, or app command non-interactively (`CI=1`, watch and UI modes off), never leave a watcher, dev server, or REPL alive past the command that needed it, and never signal a process you did not start. Append every launched leader PID to `<owned-pgids>`, the set the I1 machine guard resets each iteration.
- Constraints: read the repo's CLAUDE.md/AGENTS.md non-negotiables; else its documented conventions.
- Worktree safety: record `<invoking-worktree>`, the output of `git rev-parse --show-toplevel`, and whether it is linked: `git rev-parse --git-dir` differs from `git rev-parse --git-common-dir`. The default branch checked out in another worktree is the normal state of a linked worktree and is never a stop. Never switch, fast-forward, reset, commit to, stash, or clean `<invoking-worktree>`: every branch operation of this loop runs in a run-owned worktree under `<worktree-root>`, which starts clean at an exact commit, so no uncommitted work enters a batch and no checked-out branch moves. Save every tracked path under `.beads/` (`git ls-files .beads`) as `<excluded-paths>`: with export on, `bd` rewrites `.beads/issues.jsonl` after its own writes (`bd` 1.3.0 writes it into the worktree of the root repository, whichever worktree runs `bd`), and that tracker churn is never staged, committed, or cleaned by this loop. Carry the list as context through planning, simplification, and review-fix commits; when non-empty, pass the documented `exclude:<comma-separated-paths>` carrier to `ce-commit-push-pr`. Do not pass that carrier to a child that does not document it: `ce-work` inventories pre-work WIP itself and must block on collisions. Verify excluded paths remain uncommitted before every push. Never reset, clean, stash, or use a tree-wide checkout to make a tree look clean. If planned work collides with an excluded path, stop the batch rather than absorbing or discarding it.
- Owner-decision issues: an issue is one only when its `issue_type` is `decision` and its body says the loop may choose; find them by that content, not by hardcoded id. The scan itself does NOT run here -- it runs in I2, immediately after that iteration's CENSUS, over the issues that census classified as neither `human-gate` nor `label-defect`. `## HUMAN GATES` owns why, and the order is not optional.

## CLEAN-TREE GATE RUN

Every gate whose result authorizes a merge -- the I1 trunk gate, the P6 pre-PR gate, and I7 post-merge verification -- runs against a throwaway worktree at an exact commit, never in the working tree.



- `<clean-tree>` is `<worktree-root>/<sha>`, where `<worktree-root>` is a single run-owned directory outside every worktree of this repository, named after `<run-id>`, contains no whitespace, and is recorded once in the ledger as `backlog_loop_worktrees`. `git worktree add --detach <clean-tree> <sha>`. When any gate or application command may invoke Docker Compose, give this tree one unique `<compose-project>` derived from the run id and SHA, restricted to Compose's lowercase project-name alphabet. Resolve `<docker-context>` with `docker context show`, require it to contain neither whitespace nor `@`, and append `<compose-project>@<docker-context>@<clean-tree>` to `backlog_loop_compose_projects` on every batch member before starting the command. Pass the exact project through `COMPOSE_PROJECT_NAME`; invoke Compose through `docker --context <docker-context> compose`; and require the command to use the Compose configuration resolved from `<clean-tree>`. A command that needs `-f`/`--file`, `--project-directory`, `--env-file`, `-p`/`--project-name`, an unrecorded `DOCKER_HOST`, or a different Docker context has no replayable cleanup record and blocks before start. Never reuse the repository's default Compose project.
- `<worktree-root>` lies outside every worktree of this repository: its path is neither inside nor above any path `git worktree list --porcelain` names, and not inside `git rev-parse --git-common-dir`. Every worktree this loop creates sits directly under it. Only a path under it is ever removed, with `git worktree remove --force <path>`, which also clears a registration whose directory is already gone; nothing here prunes repository-wide, because a prune also drops the registration of any worktree of the operator whose directory is temporarily missing.
- `<trunk-tree>` is `<worktree-root>/trunk`, the run-owned worktree that holds the trunk checkout and every batch, TRUNK REPAIR included. I1 creates it with `git worktree add --detach <trunk-tree> <remote>/<default>` when it is absent and otherwise moves it with `git -C <trunk-tree> switch --detach <remote>/<default>`. It is detached and holds no branch; the work branch `ce-work` cuts there starts from `<batch-base-sha>`. ITERATION steps 3 through 7 run every child skill with `<trunk-tree>` as the working directory, never `<invoking-worktree>`.
- If the gate set needs installed dependencies, run the repo's documented install or bootstrap command inside every run-owned worktree a child skill or gate runs in -- `<trunk-tree>`, `pr-<number>`, and `<clean-tree>` -- before the first one runs there, preferring its frozen/locked form. Then require `git status --porcelain` in that worktree to report no change to a tracked file. Any tracked change -> the gate has not passed. A gate that cannot execute there has not passed either, and neither may be recorded as green.
- Run the gates there under the same process-hygiene rules, including the run token and `<owned-pgids>`. A command that may invoke Compose runs from `<clean-tree>` with `COMPOSE_PROJECT_NAME=<compose-project>` inside a shell that installs its cleanup trap BEFORE the command starts. The `EXIT` trap captures the command status, disables its own signal traps, runs `docker --context <docker-context> compose -p <compose-project> down --remove-orphans`, and requires the exact project name to be absent from `docker --context <docker-context> compose ls --all --quiet`. Cleanup success returns the original command status. Cleanup failure returns non-zero even when the command succeeded, while an already non-zero command keeps its original status, so every failure blocks; `HUP`, `INT`, and `TERM` traps exit non-zero so the `EXIT` trap still runs. A trailing `docker compose down` line is not equivalent.
- Before removing a Compose-owning worktree on either the green or red path, repeat that teardown idempotently from `<clean-tree>` with the recorded context and require the exact project name to be absent from `docker --context <docker-context> compose ls --all --quiet`. Only then retire that `<compose-project>@<docker-context>@<clean-tree>` record from every batch member, and run `git worktree remove --force <clean-tree>`, which also clears the registration of a tree whose directory is already gone. A failed teardown keeps the worktree and its ledger record for RECOVERY and blocks the batch.

Tag every claimed member with `bd update <id> --set-metadata backlog_loop_run=<run-id>`; remove that metadata from members dropped before implementation.

Do not resolve a plans directory here. `ce-plan`, under LFG's `plan-brief.md` contract, resolves its own artifact root and reports the path it wrote; I5 uses that reported path and nothing else.

## BATCH BUDGET

```
TARGET   = 90 minutes of estimate   # fill a batch toward this
CEILING  = 150 minutes              # never admit a member that crosses this
CONCERNS = 4 members maximum        # review cost scales with concern count, not only size
```

Estimates come from the tracker's own field (`bd show --json` -> `estimated_minutes`). When an issue has none, derive one from this rubric and write it back with `bd update <id> --estimate <minutes>`:

| Shape of the issue | Minutes |
|---|---|
| Docs/config/copy only, one file | 15 |
| Bug with a clear repro, one module | 30 |
| Task with 1-3 acceptance criteria, one module | 45 |
| Feature, or anything crossing modules | 90 |
| Vague, or touching auth/payments/migrations/external contracts | 120, and treat as solo |

## STATE

State lives in the tracker. Re-read `bd ready --json --limit 0` every iteration; never work from a remembered list. Every `bd ready` call carries `--limit 0`: without it the tracker returns at most 100 rows, so a larger backlog reads as a smaller one. Also inspect non-epic `in_progress` issues and split them by the PRESENCE of `backlog_loop_run` metadata, never by its value.

- Marker present: an earlier run of this procedure claimed it and did not finish. Recover it through THE RUN LEDGER below.
- Marker absent: externally owned. Never steal it. If no ready work exists and one of these remains, stop and report that the backlog is not clear.

That split is an ownership test and CENSUS extends it into a full accounting of every non-closed issue. A `needs-person` cause alone on a blocked issue marks this loop's own release of a person-closed PR, even after its RUN keys are unset. Read CENSUS before deciding that anything is finished.

| class | members | unset by |
|---|---|---|

A drop is a member released before implementation; it has no forge link to unset. A human-close release is LINKED PR DISPOSITION's `CLOSED` row.

LIVENESS, before any recovery. A marker proves an earlier run claimed the issue; it does not prove that run stopped. Read `backlog_loop_heartbeat`, whose value is `<iso> | live` or `<iso> | released`; a value with no suffix is a legacy `live`. `live` and less than 30 minutes old, or any live process carries that run's `BACKLOG_LOOP_RUN` token AND that run belongs to this repository -> another invocation is still working. A run belongs to this repository when its run-id is the `backlog_loop_run` or `backlog_loop_census` of an issue in this tracker, or when a worktree it created appears in this repository's `git worktree list`. A token found on a process of another repository's loop (the process tree's cwd is another repository, and neither test matches) is that repository's run: ignore it for LIVENESS, the census, and I8 REAP, and never signal it. The token scan reads every process on the machine, so the repository test is what keeps two projects' loops from stopping each other. `released`, a stale `live`, and an absent heartbeat are dead unless such a process exists. A process that also carries `BACKLOG_LOOP_ROLE=refresher` is a refresher, and a refresher alone does not prove a live run: it outlives a dead run by up to 6 hours. STOP and report a live run. Do not reap, reclaim, park a PR, or claim anything.

HEARTBEAT REFRESHER. The first time an iteration stamps a `live` heartbeat (CLAIM or ADOPTION), launch one refresher under process hygiene: `perl -e 'setpgrp(0,0); exec @ARGV' -- sh -c 'n=0; while [ "$n" -lt 36 ]; do <refresh> || break; n=$((n+1)); sleep 600; done'`, with `BACKLOG_LOOP_RUN=<run-id>` and `BACKLOG_LOOP_ROLE=refresher` exported and its leader PID appended to `<owned-pgids>`. It is the one command here with no `<gate-timeout>`, so its lifetime is bounded another way: 36 ticks (6 hours), and it stops at the first `<refresh>` that fails or that finds no `in_progress` issue carrying `backlog_loop_run=<run-id>`. A run that died without REAP therefore leaves no refresher alive after 6 hours. A stage boundary that finds the refresher's group gone launches it again, so a live run is never left without one. I8 REAP ends it with the iteration's other groups. Every 10 minutes it refreshes every `in_progress` issue carrying `backlog_loop_run=<run-id>`: it writes `backlog_loop_heartbeat="<iso> | live"` and runs `bd heartbeat <id>`, which renews the claim lease and refuses a parked issue. Run the same refresh yourself at every pipeline stage boundary, I5 through I7.

RECOVERY, by the recorded phase. Read it before touching anything.

- `merged` or `verified`: the merge is proven. For `verified`, finish the interrupted Beads close. For `merged`, inspect the durable `backlog_loop_postmerge_ci` queue entry and poll every expected workflow on the recorded merge SHA. With both recorded CI routes `on`, a missing or in-progress expected run is pending, never green, until 30 minutes have passed from the original first-seen time; then run step 7's exact-merge local gate once. If either route is `off` or missing, a missing workflow does not hold verification after the exact-merge clean-tree gate passes; an observed red workflow still enters TRUNK REPAIR. Resume I7 with the original first-seen time; never restart its 30-minute allowance on recovery. A failed run enters TRUNK REPAIR after reproducing or ruling out the failure on current trunk. When verification passes, write `verified` as I7 does, heartbeat unset in that write, add the calibration note, and `bd close` against `backlog_loop_pr`. If either recorded CI route is `off` or missing, also run the clean-tree post-merge gate at the merge SHA. A red local gate keeps the members `in_progress` at `merged` and enters TRUNK REPAIR.
- `merge-requested`: the outcome is unknown, which is exactly what this phase exists to record. Query `backlog_loop_pr` and apply LINKED PR DISPOSITION to its state; `MERGED` is the common answer and means treat as `merged` above.
- `shipping-requested`: the push and PR creation were requested but their identifiers were never recorded, so a PR may exist under a URL the ledger does not hold. Search for it by the recorded branch and head - `gh pr list --head <backlog_loop_branch> --state all --json number,url,state,headRefOid,baseRefName` - record the URL of a single match in `backlog_loop_pr`, and apply LINKED PR DISPOSITION to it. No match -> reclaim. More than one match -> the table's more-than-one-PR row: this issue alone goes to `needs-person`, and the run continues.
- `pr-open`, `built`, or `claimed`: query `backlog_loop_pr` when present; otherwise, when `backlog_loop_branch` is recorded, run the `shipping-requested` arm's branch search, because the branch is recorded at P3, before any phase past `claimed`, and a recorded branch may already carry a PR. Apply LINKED PR DISPOSITION to the PR found. No PR -> reclaim. Never resume a half-built branch into a merge; it is rebuilt.
- Absent, or any value the `backlog_loop_phase` row above does not list: an unrecognized phase is a claim about a state this procedure does not define, so the value itself is never read as a phase. Decide from the ledger's other keys instead, which record what actually happened, in this order. `backlog_loop_merge` recorded -> treat as `merged` above. Else `backlog_loop_pr` recorded -> query it and follow the `merge-requested` arm's rules. Else `backlog_loop_branch` recorded -> follow the `shipping-requested` arm's search, its scoped `needs-person` on more than one match included. Else reclaim. Name the unrecognized value, the arm taken, and the evidence key that chose it in the FINAL REPORT: an improvised value was written by something, and a recovery that swallows it leaves the next run to meet the same value with the same nothing to go on. Without this arm an unrecognized phase matches no arm at all and ends the run outright -- which is how one issue carrying one improvised value wedged every later invocation.

LINKED PR DISPOSITION. Every entry point that holds a PR URL -- a RECOVERY arm above, OPEN PR RESUME, I6's failure paths, and P8 -- reads the PR's forge state once and takes the action of the first row below that matches, top to bottom. The recorded phase decides only how the URL is found; this table decides what happens to the PR. The first matching row wins, and the last row is the catch-all for unnamed open states. "Charged" is defined under CHARGING.

ADOPTION. A parked PR is adopted by one write, guarded so two invocations cannot both take it: `bd update <id> --if-status blocked --status=in_progress --assignee <actor> --set-metadata backlog_loop_run=<run-id> --set-metadata backlog_loop_heartbeat="<iso> | live"`. The write stamps the RUN-class run and heartbeat, so the adopted issue classifies as `claimed-this-run`. Read the issue back and require status `in_progress`, assignee `<actor>`, and `backlog_loop_run=<run-id>`. Any nonzero exit with an unchanged read-back means another invocation adopted it first: skip the issue and write nothing. Exit 13 is the status guard, but a second adopter that names its own assignee is refused with exit 1 before the guard is reached, so never read the exit code alone. Adopt a PR's members in ascending id order; losing the first member skips the PR this iteration. After a won adoption run `bd heartbeat <id>` and start the HEARTBEAT REFRESHER when this iteration has none. A member still `in_progress` under a dead run (RECOVERY) is parked first, never adopted in place: re-read its status and `backlog_loop_run`, skip it when either changed, then one `bd update <id> --if-status in_progress --status=blocked --unset-metadata backlog_loop_heartbeat --set-metadata backlog_loop_cause=transient:pr-open`, uncharged, and adopt it with the write above. Exit 13 means another invocation moved the member first: skip it and write nothing.

Every write that sets `blocked`, in the table above or anywhere below, carries `--unset-metadata backlog_loop_heartbeat` in that same command.

CHARGING. A charge is `backlog_loop_attempts` and `backlog_loop_attempts_total` each set to its current value plus one (an absent total starts from the attempts value), read back after the write. Charged: a pipeline block on work this loop authored, a guarded-merge refusal after such work, and each row above marked charged. Never charged: a poll, a pending check, a trunk move at P6 or in the base-behind row, waiting on a required approval, an interruption park in RECOVERY, and every row that goes straight to `needs-person`. The ceiling `<attempt-ceiling>=3` bounds one issue across its whole life for every cause, `transient:pr-open` included, and REOPEN PASS enforces it. A member stamped `backlog_loop_trunk_repair` has the higher ceiling `<repair-attempt-ceiling>=5` instead, because a red trunk stops every merge and one more diagnosed attempt costs less than the stall. There is no run-level counter: a scoped PR never stops independent work.

Never close a PR automatically. A PR this procedure cannot land stays open. Parking it means keeping its branch and `backlog_loop_pr` ledger link, setting its issue to `blocked` with `backlog_loop_cause=transient:pr-open`, and reporting the exact pending gate or review. Do not reclaim or rebuild that issue while its PR is open. Every later loop invocation rechecks that PR through OPEN PR RESUME, which applies the table after refreshing its head, base, review, and verification state. Only a row that needs a person's action becomes `needs-person`. Reclaim only when no PR exists for the recorded branch.

Reclaim means `bd update <id> --status=open --assignee="" --unset-metadata backlog_loop_run --append-notes="reclaimed from interrupted run <old-run-id> at phase <phase>"`, plus unsetting the rest of the RUN class and the FORGE-LINK class (KEY CLASSES), returning the issue to `bd ready`. No DURABLE key is unset: the attempt count, cause, quarantine, edge records, and trunk-repair mark outlive every reclaim.

Before any of that, and only after LIVENESS has proved the old run is gone, reap its escaped processes by its `<old-run-id>` token exactly as I8 does. Then read every `backlog_loop_compose_projects` record, run the CLEAN-TREE teardown from its recorded worktree through its recorded Docker context, and require the project absent from `docker --context <docker-context> compose ls --all --quiet` before removing that worktree. A missing tree or failed teardown is a recovery blocker and is reported with the exact project name; never delete the remaining worktree root and strand the stack. After every recorded project is absent, remove every worktree registered under `backlog_loop_worktrees` with `git worktree remove --force <path>`, which also clears a registration whose directory is already gone, then delete the emptied directory with `rmdir`; never prune repository-wide, so an interrupted run's worktrees and their installed dependencies do not accumulate on disk until a later gate cannot create one.

There is deliberately no run-global failed-batch or failed-merge counter. `<owned-pgids>` is in-memory by design, which is why every command also carries the run token - the token is what makes a dead run's processes findable when its PID list is gone. A failed or blocked attempted batch is marked `blocked`, so it cannot be selected again silently. An open linked PR is the exception: OPEN PR RESUME rechecks the existing PR without rebuilding it or charging another attempt for each poll. `backlog_loop_attempts` bounds one ISSUE across its whole life. CI is batch-scoped and re-resolved from the exact current trunk SHA every iteration; it may change in either direction.

## CENSUS

One classification pass over the whole tracker, written once and read by both entry points. Both evaluate the same recorded fields under the same stated precedence, so a category difference between a diagnostic run and a loop run over an unchanged backlog is a defect -- in this section, the fixture, or the tracker -- and never a permitted outcome. The loop runs it at the termination decision; the companion census prompt runs it alone. Nothing below infers termination from an empty `bd ready` list.

Choose a `<census-run>` token the same way as `<run-id>`.

ENUMERATE. `bd list --all --limit 0 --include-gates --json`, then discard `status=closed` and `issue_type=epic` rows. Every flag is load-bearing: `--limit 0` lifts the 50-row cap, `--include-gates` adds native gate issues, `--all` adds `pinned` issues, and the closed rows it returns are discarded in the query. Do NOT pass `--include-infra` or `--include-templates`: agent, role, message, and template beads are not work, have no category below, and would make the exhaustiveness claim false. Say so on the census header line, so an operator reading a count knows what it counted.

`bd ready --explain --json --limit 0` is the AUTHORITY for the dependency question -- which issues are dependency-blocked, and by what -- and not merely a source of blocker names. Do not re-derive it from edges. Count its rows: the `ready` and `blocked` arrays must hold `summary.total_ready` and `summary.total_blocked` rows, and a shortfall is a truncated read, so name the gap and retry as ACCOUNT FOR THE COUNT does.

That explanation covers OPEN issues only. A `blocked` issue appears in neither of its buckets, so every category below that turns on `status` is read from the issue's own stored status.

METADATA IS NOT RELIED ON IN THE ENUMERATION. Whether `bd list --json` carries a `metadata` object or a `dependencies` array depends on the `bd` version: 1.3.0 returns `metadata` on a row that has any and `dependency_count`, but no `dependencies` array to resolve it with. So the marker-bearing rows below are answered by one `bd list --has-metadata-key <key> --json` per marker key -- `backlog_loop_run`, `backlog_loop_cause`, `backlog_loop_quarantine`, `backlog_loop_heartbeat`, `backlog_loop_census_heartbeat` -- intersected with the enumeration.

BACKFILL, once per issue, BEFORE the precedence walk below. A `blocked` issue carrying `backlog_loop_run` but no `backlog_loop_cause` predates this section: it was written by an earlier form of the procedure that recorded only a note. It covers only blocks that already carry a marker; a block with no marker at all is older still, and row 13 handles it without writing anything.

- The note text is not in the enumeration output, so read it with one `bd show <id> --json` per affected issue. That is the one place a per-issue query is allowed, and it is bounded twice over: only `blocked` marker-bearing issues with no cause qualify, and an issue that has a cause key is never re-read.
- Classify it with I7's cause list only: a note beginning `merge blocked; PR remains open:` backfills as `transient:pr-open`, a `pipeline blocked:` note whose reason says trunk moved as `transient:trunk-moved`, a `pipeline blocked:` note whose reason begins `gate failed:` as `transient:gate-failed`, a `pipeline blocked:` note whose reason begins `review residual:` as `transient:review-residual`, a `pipeline blocked:` note whose reason begins `tool failure:` as `transient:tool-failure`, and every other note, including the legacy prefix `post-merge verification failed:` that nothing writes now, as `needs-person`.
- Derive the cause in BOTH modes; PERSIST it only when the WRITE GATE below allows. A diagnostic run classifies on the derived value and writes nothing, which is what lets `--readonly` hold. Persisting means `backlog_loop_cause=<derived>` plus `backlog_loop_attempts=1`.

CLASSIFY. Every enumerated issue gets exactly one category. Walk this precedence top-down and stop at the first match:

An `abandoned-claim` is never selected directly. It is this procedure's own wreckage and it goes through THE RUN LEDGER's RECOVERY, which reads `backlog_loop_phase` and decides per phase whether to reclaim, adopt the existing PR, or leave it; only what recovery returns to `open` can be picked in a later iteration.

Two different rules govern the marker. `## STATE`'s rule -- split by the PRESENCE of `backlog_loop_run`, never its value -- decides ownership: present means this procedure's own work, recoverable through THE RUN LEDGER; absent means externally owned and never to be stolen. Rows 4, 8, and 12 are not an ownership question but a liveness one, and they are the ONLY place the marker's value is read, always together with `backlog_loop_heartbeat` under the liveness test. A stale marker with a dead heartbeat therefore still classifies as this procedure's own wreckage -- as row 12 for an unfinished claim, as rows 6 and 7 for a block -- exactly as `## STATE` requires.

EMIT, always, in both modes. One line per enumerated issue, in this exact shape:

One line per issue and nothing else on it.

ACCOUNT FOR THE COUNT before reporting anything. The number of `census ` lines must equal the number of rows the enumeration kept. On a mismatch, name the missing ids and retry only those reads up to three times, reclassifying and recounting after each bounded retry. A recovered read continues normally. A persistent mismatch is tracker-wide incomplete evidence, so do not report a census or enter a mutation pass; apply `## STOP EARLY AND REPORT` because no batch can be selected safely from an incomplete population.

Print the header line first, beginning with the literal `census-run ` and carrying the census token, the counts per category with `auto-resolving` gates split out of the `human-gate` count as their own figure, and the flags the enumeration ran under. The two prefixes are fixed and distinct on purpose.

LOOP-RESPONSIBLE SET. Exactly five categories are the loop's to clear: `ready`, `claimed-this-run`, `abandoned-claim`, `self-blocked-transient`, and a `dep-blocked` issue whose blocker is itself in one of those. An issue whose open linked PR REPORT lists as awaiting a required approval is reported as awaiting a person and does not hold back the clear verdict. Everything else is somebody's or something else's. `quarantined`, `legacy-blocked`, and `self-blocked-needs-person` are deliberately NOT in the set, because they wait on a person. The backlog is clear when no issue sits in that set -- never because `bd ready` came back empty.

Walking `dep-blocked` transitively meets the cycles this procedure reports and never repairs, so the walk carries a visited set, counts each issue at most once, and treats a repeat visit as the end of that branch plus a reported cycle. Walk the `blocked_by` lists in the `bd ready --explain --json --limit 0` output already taken above, which reports its own cycle count; the enumeration carries no edges to walk.

WRITE GATE, covering EVERY write this section makes -- the BACKFILL persist above and every mutation pass below (REOPEN PASS, RESIDUE PASS, and GATE REPAIR PASS), not the passes alone. Each is skipped entirely, with no partial application, when either of these holds: the run is a diagnostic run, or any other run of this procedure holds a live heartbeat. The `<repair-ceiling>` is a third stop but a narrower one: it bounds GATE REPAIR PASS only, and never stops REOPEN PASS, which is bounded per issue by `backlog_loop_attempts`, or RESIDUE PASS, which writes at most once per issue and then never again. A skipped write still classifies, still emits, and still reports every action it would have taken.

"Another run holds a live heartbeat" means either of two things, and both are decided from a field that says WHOSE it is: a `live` `backlog_loop_heartbeat` under 30 minutes old on an issue whose `backlog_loop_run` is present and is not `<run-id>` (a `released` heartbeat, a stale one, and one with no `backlog_loop_run` beside it are not), or a `backlog_loop_census_heartbeat` under 30 minutes old whose token is not `<census-run>`.

Before any pass, publish the second of those: `bd update <id> --set-metadata backlog_loop_census_heartbeat="<census-run> | <iso-time>"` on the issue that pass is about to write to. The value carries `<census-run>`, so ownership is decidable from the field alone. Re-read before each individual mutation rather than once for the whole pass; a value whose token is `<census-run>` is this run's own and is ignored.

Repairs are idempotent, not ledger-phased. Every repair below instead re-reads current state and does nothing when it is already applied, which makes recovery "run the census again".

REOPEN PASS. For each `self-blocked-transient` issue, in ascending id order:

- `backlog_loop_attempts` at or above its ceiling (`<attempt-ceiling>=3`, or `<repair-attempt-ceiling>=5` for a trunk-repair member) for any cause, `transient:pr-open` included -> rewrite `backlog_loop_cause=needs-person`, write the ESCALATION DOSSIER below, write `backlog_loop_ceiling` in that same command when the prior cause was `transient:gate-failed`, `transient:review-residual`, or `transient:tool-failure`, name it in the report, and never reopen it again. No cause is exempt, and this count never resets.
- ESCALATION DOSSIER, written once with that rewrite: one `--append-notes` entry that lists, per attempt, the date, the failing command, its exact error, and the `retry-hypothesis` tried; then the strongest remaining suspicion, and the exact command a person runs to grant one more attempt (`bd update <id> --status=open --assignee="" --unset-metadata backlog_loop_run --set-metadata backlog_loop_cause=transient:gate-failed --set-metadata backlog_loop_attempts=<ceiling-1>`). Report that command beside the issue. This step never creates an issue and never writes the `human-gate` label, which stays author-only; independent ready work keeps flowing.
- Otherwise prove the recorded cause is gone before touching it. The cause is a recorded value, not a reading of the note: `transient:trunk-moved` is gone when `<remote>/<default>` is currently green under the recorded `backlog_loop_trunk_ci` route (missing -> local clean-tree gate); a PR-head check does not prove trunk health. The legacy `transient:merge-precondition` is gone when the recorded PR is `CLOSED` and no PR is open on the recorded branch. `transient:gate-failed`, `transient:review-residual`, and `transient:tool-failure` are gone when `backlog_loop_attempts` is below the ceiling: the failure is a defect this loop can fix, so reopen it, and the next claim reads the recorded failing command and error from the notes and reproduces it first. A `transient:tool-failure` waits `<tool-retry-delay>=15m` after its block note first, so a flaky service is not hit again at once. Trunk-repair members take this path too; never leave one at `needs-person` below the ceiling. `transient:pr-open` is handled by OPEN PR RESUME, never by reopening this issue; skip it in this pass except for the ceiling above. A `MERGED` PR is NOT that proof, even though a merged PR is also a closed one: the work is already on trunk, so reopening rebuilds shipped code. Read the PR's state explicitly and require `CLOSED`; on `MERGED`, leave the issue for LINKED PR DISPOSITION's `MERGED` row, which verifies and closes it. A bare `transient` with no subtype, or any cause with no proof the census can evaluate on its own, is not a transient cause at all: record it `needs-person` rather than leaving it to expire on a condition nothing can satisfy.
- Proven -> one atomic update, following the reclaim shape: `bd update <id> --status=open --assignee="" --unset-metadata backlog_loop_run --append-notes="reopened by census <census-run>: <cause> no longer holds"`, plus unsetting every other RUN-class and FORGE-LINK-class key (KEY CLASSES). DURABLE keys are deliberately NOT cleared: the attempt count is what bounds the cycle.
- A legacy block whose note begins `post-merge verification failed:` (an earlier form of this procedure wrote it; nothing writes it now) is never reopened, whatever trunk currently looks like. Its code is already on trunk and its phase is already `merged`; the proven-merge rule in THE RUN LEDGER says that work is finished, not rebuilt. LINKED PR DISPOSITION's `MERGED` row returns its member to `in_progress` at `merged`, so I7's CI watch or repair disposition takes it; never rebuild its merged code.

PROBATION PASS. A ceiling is a pause, not a verdict, when the work failed for a reason a later state can change. For each `self-blocked-needs-person` issue that carries `backlog_loop_ceiling` (`<iso> | <trunk-sha> | <skill-digest> | <prior-cause>`, written only when the ceiling rule rewrote a `transient:gate-failed`, `transient:review-residual`, or `transient:tool-failure` cause), in ascending id order:

- Skip it when `backlog_loop_attempts_total` is at or above `<lifetime-attempt-cap>=9`; that count never resets, and the issue stays `needs-person` for good. An issue with no `backlog_loop_attempts_total` counts as `backlog_loop_attempts`.

Mismatch -> blocked path. Only then write `backlog_loop_pr` and `backlog_loop_phase=pr-open` for every member.

Run `compound-engineering:ce-babysit-pr mode:pipeline <pr-url>` whenever a loop PR exists, on either CI route and with or without required checks, and keep the PR open until its decision: success goes to the merge gate, a `needs-human` return is `needs-person`, and an exhausted budget or a red residual is the charged blocked path in I7. Required status checks must appear and pass. If the babysitter changes the head, write `backlog_loop_head` at once and return to P4-P6 for that head (at most two rounds, then the blocked path in I7). A completed failure of any required check on the exact head blocks the merge; a completed optional failure blocks unless it is `startup_failure` or a billing or quota error. Re-read the head, required checks, `mergeStateStatus`, and `reviewDecision` immediately before merge. Never close a PR because CI did not start or finish.

Do not impose a quiet period or close the PR because a review did not finish.

Unchecked entries are undecided findings and cannot cross an autonomous merge gate; `advisory` findings are not entries and never block a merge. Any blocked, failed, malformed, red-required-check, missing-PR, or decision-needed result takes the blocked path in I7.

With `<batch-ci>=off`, the final local pre-PR gate is the authority. Required checks must pass, and a completed failure of an optional check blocks too unless it is `startup_failure` or a billing or quota error; only a missing or pending optional check, including those errors, is bypassed by green exact-head local gates. Keep the PR linked to its blocked issue if that guard fails. Do not use GitHub auto-merge. Before issuing the merge, set `backlog_loop_phase=merge-requested` on every member. Then run `gh pr merge <url> --squash --match-head-commit <batch-head-sha>`, exactly one merge per batch. Never pass `--admin`, and never `--delete-branch`: its local cleanup switches the checkout to `<default>` and deletes the local head branch, which a worktree that holds either one refuses, and the refusal can leave the remote branch undeleted.

   The command's exit status decides nothing. Poll `gh pr view <url> --json state,mergeCommit` every 30s under a bounded 10-minute deadline after EVERY merge invocation, whatever it returned.

   `MERGED` -> record its merge commit as `<merge-sha>`, then require `git merge-base --is-ancestor <merge-sha> <remote>/<default>` after a fetch. Write `backlog_loop_merge` and `backlog_loop_phase=merged` for every member. Then delete the remote head branch with `gh api -X DELETE repos/{owner}/{repo}/git/refs/heads/<branch>`: a missing reference means GitHub already deleted it, any other failure is reported, and the proven merge stands either way.

If it is now `MERGEABLE` at the gated head with no required check pending, retry the guarded merge once; optional review activity is not a blocker. Otherwise apply LINKED PR DISPOSITION to the re-read state and report the exact reason. Never close the PR automatically.

   Members stay `in_progress` at `merge-requested` while the outcome is unknown. Once the PR is proven `OPEN` and unmerged but cannot pass the guarded merge, park every member as the matching row says: `bd update <id> --status=blocked --unset-metadata backlog_loop_heartbeat --append-notes="merge blocked; PR remains open: <reason> | <url>" --set-metadata backlog_loop_cause=transient:pr-open`, plus `--set-metadata backlog_loop_attempts=<n+1>` when that row is charged, reading the issue's current count first. Keep the PR URL, branch, and head in the ledger, sync when configured, count the batch blocked, and continue independent work. Never force a merge or create a duplicate PR for the parked issue.

A disabled workflow, and a `pull_request`, `workflow_dispatch`, or `schedule` workflow the merge did not trigger, is not expected. Query every expected workflow on the exact merge SHA, reducing reruns to the latest attempt per workflow. When both CI routes are `on`, a missing or in-progress expected result remains pending until that deadline. When either route is `off`, the exact-merge local gate is authoritative: a missing workflow does not keep the queue pending after that gate passes. An observed terminal red workflow still enters TRUNK REPAIR. Wait up to 30 minutes total from `<first-seen-utc>`. An entry still pending at that deadline stops waiting: run the applicable local quality gate set once through CLEAN-TREE GATE RUN at `<merge-sha>`, in a clean worktree, and write the entry `timeout-local-green` when it is green or `failed` when it is red, so the gate never runs twice for one entry; a result the route-`off` gate below already recorded for this `<merge-sha>` is that run. Green closes the members with the `timeout-local-green` receipt in the close reason; red enters TRUNK REPAIR with the gate's evidence. Until the deadline, retain each member `in_progress` at `merged`, keep its PR and merge SHA, report the pending workflow URLs, and proceed to independent ready issues. Recheck the durable queue at each iteration and in the next invocation. Do not call `bd close` while any required expected workflow is pending inside its 30 minutes. A terminal red CI result enters TRUNK REPAIR with its job, command, and log evidence; if trunk has advanced, verify whether the failure persists on current trunk before changing code. If `<batch-ci>=off` OR `<trunk-ci>=off`, also update trunk safely, derive changed files from `<merge-sha>`, and run the applicable quality gate set once through CLEAN-TREE GATE RUN at `<merge-sha>`. Red local gates enter TRUNK REPAIR. Never rebuild code already merged.
   When every required expected exact-merge CI workflow and every applicable local gate is green (including the local gate in place of missing CI when either route is `off`), write `bd update <id> --set-metadata backlog_loop_postmerge_ci="<merge-sha> | <first-seen-utc> | passed" --set-metadata backlog_loop_phase=verified --unset-metadata backlog_loop_heartbeat`; `bd close` takes no metadata flag, so the heartbeat goes in this last write before it. A local-gate timeout writes `timeout-local-green` in place of `passed` in that same command. A red exact-merge result remains `failed` until TRUNK REPAIR makes current trunk green or a later commit is proven to have resolved that same failure; record the repair issue or resolving commit on the original member, then mark it `verified` without pretending the original run passed. Require every current gate worktree removed and every `backlog_loop_compose_projects` record retired before closing; an unproved teardown keeps members `in_progress` at their current merged phase for RECOVERY. Append calibration notes from the final PR/merge diff, then `bd close <id> --reason="<one line> | <url>"` for every member and sync. A code-caused red result keeps members `in_progress` at `merged` until TRUNK REPAIR makes current trunk green and records how the original failure was resolved.
   If the selected route returned blocked or failed in I5, no retry: for every member use `bd update <id> --status=blocked --unset-metadata backlog_loop_heartbeat --append-notes="pipeline blocked: <reason> | <url-if-any>" --set-metadata backlog_loop_cause=<class>`, plus `--set-metadata backlog_loop_attempts=<n+1>` (CHARGING), then sync. `<class>` is exactly one of `transient:trunk-moved` (trunk moved during the pipeline; uncharged, so the write omits the attempts flag), `transient:pr-open` (an open linked PR that LINKED PR DISPOSITION parks), `transient:gate-failed` (a required quality gate or test failed on code this loop authored, so the defect is agent-fixable; charged, and the note carries the failing command and its error), `transient:review-residual` (the reason begins `review residual:`; the review left only findings that change no behavior, contract, or permission and need no design decision, such as a documentation note or a stale comment, and none is a `settled_conflict`, a `needs-human` residual, or a repeat of an earlier one; charged, and the note lists every finding with `file:line`, title, and `suggested_fix`), `transient:tool-failure` (the reason begins `tool failure:`; a child skill or tool failed for a reason outside the code under change: a review return with `failed`, `degraded`, or `skipped` status or a malformed return, a child that crashed or timed out, a pipeline interrupted mid-run, or a teardown that could not be proved; charged, and the note names the tool and its exact error), or `needs-person`; any other reason is `needs-person`, never an unqualified `transient`. The PR remains recoverable through OPEN PR RESUME without another attempt charge per poll. Read the current `backlog_loop_attempts` first and write that value plus one. Every member counts as attempted.
   Either way print one line per member - `<id> | <title> | <url> | merged|blocked` - plus one `batch: <id>,<id>,... | est <n> min | actual <k> files` line.

8. **REAP.** Runs at the end of every iteration - merged, blocked, or stopped early - before I1 of the next batch and before any early-stop report returns.
   - For every `<pgid>` in `<owned-pgids>` still listed by `ps -Ao pgid=`: first re-prove ownership by requiring some current member of that group to carry this run's `BACKLOG_LOOP_RUN` token. Proven -> `kill -TERM -<pgid>`, wait 5s, then `kill -KILL -<pgid>` if it survives. Not proven -> report it, never signal it. Kill the group, never the leader alone.
   - For every port in `<owned-ports>`, list its listeners with `lsof -i :<port> -sTCP:LISTEN -t`, take each listener's process group, and treat that group exactly like a `<pgid>` above: proven by this run's token -> TERM, then KILL after 5s; not proven -> report it, never signal it. This is how the dev server `ce-test-browser` left running is stopped, and its log is `/tmp/dev-server-<port>.log`.
   - Then sweep only what this run provably owns: processes whose environment carries `BACKLOG_LOOP_RUN=<run-id>`, read with the platform's environment-listing form of `ps`. TERM, then KILL after 5s. For every `backlog_loop_compose_projects` record, run the CLEAN-TREE teardown from its recorded tree through its recorded Docker context and require the exact project absent from `docker --context <docker-context> compose ls --all --quiet`; only then remove that `<clean-tree>` worktree. If teardown cannot be proved, keep the tree and record, report the exact project, and take the blocked path instead of leaking it behind successful cleanup. After those records are retired, remove every other run-owned worktree -- `<trunk-tree>`, a `<clean-tree>`, or a `pr-<number>` worktree -- with `git worktree remove --force <path>`, and only for a path under `<worktree-root>` that `git worktree list --porcelain` registers; a worktree outside `<worktree-root>` is never removed, whoever created it, and a tree whose Compose record remains is never eligible for that sweep. A registration whose directory is already gone is cleared by that same command, so REAP never prunes repository-wide.
   - For every batch merged this iteration, once its worktree is removed, delete its local head branch with `git branch -D <backlog_loop_branch>`: `--delete-branch` would have done it but cannot from a worktree, and nothing holds the branch now. Report a refusal and never retry it.
   - Everything else is reported, never killed. Repo path plus start time is not ownership. Never kill by tool name either: no `pkill -f vitest|node|go|python|pytest`.
   - On the run's final REAP, the one before FINAL REPORT or an early-stop report, and only after every run-owned worktree is removed and every Compose record is retired, delete `<worktree-root>` with `rmdir`: it is the run-owned directory recorded in `backlog_loop_worktrees`, `rmdir` refuses a directory that still holds anything, and a tree whose teardown failed keeps it. Remove nothing outside that directory, and never the invoking worktree.
   - Record `reaped: <n> group(s), <m> orphan(s)` on the batch line and list every killed command in the FINAL REPORT.

## HUMAN GATES

A human gate is work a person reserved for themselves -- an access grant, a credential, a paid subscription, a production approval, information only they hold. The loop never claims, plans, builds, or merges one, and never counts one as unfinished agent work. A backlog whose only remainder is gates has no agent work left in it; say that plainly rather than reporting it unclear.

RECOGNITION, decided in the census before anything else looks at the issue:

- The `human-gate` label, or `issue_type=gate`. Those are the only two signals. A native gate's `await_type` decides only how it is reported: `human` or absent waits on a person, while `timer`, `gh:run`, `gh:pr`, and `bead` resolve themselves.
- A title beginning `[HUMAN]` without the label is a `label-defect`: withheld from claiming exactly like a gate, reported with the label to apply, and repaired never. The prefix is a human convention that no query can rely on.
- Both labels named here -- `human-gate` and `hard-blocker` -- are author-only signals. NO step of this procedure ever writes either one, on any issue, in any mode.

Gate recognition runs BEFORE preflight's owner-decision content scan, and that scan sees only issues the census classified as neither `human-gate` nor `label-defect`. The distinguishing question is not what the body sounds like but what the agent can do: an owner-decision is a preference the agent can substitute for and a human reviews in the PR; a gate is an act the agent cannot perform at all. An issue matching both is treated as a gate and reported as a labeling defect.

REPORTING. Every open human or untyped gate is named in the final report with what the person must do, taken from its description, acceptance criteria, or design field; an auto-resolving gate is named with its `await_type` and no person action. All three empty -> report it as an incomplete gate.

REPAIR. The repository convention this procedure serves says a gate must not be a dependency of other work, and that any real exception is declared explicitly. So a gate holding another issue with no declaration contradicts its own recorded intent. That, and only that, is repairable here.

- The declaration is the `hard-blocker` label on the gate. Free prose is never read as one, however clearly it is written.
- ADOPTION GATE, evaluated first, every run. When NO issue anywhere in the tracker carries a `hard-blocker` label, the repository has not adopted the convention: report every undeclared gate edge with the exact label to apply, and remove none of them. The first `hard-blocker` anywhere is the operator's adoption of the convention; after it exists, the rule below applies normally.
- A native gate (`issue_type=gate`) is NEVER repaired or quarantined: its blocking edge is declared by construction, so every edge a producer such as `source-to-beads` writes on one stands. `bd create --type gate` and `bd gate create --blocks <id>` are how it comes into being, and no label is needed to declare it, so a native gate that also carries `human-gate` is still exempt and no `hard-blocker` is ever required of its producer. Report it and leave it, and never quarantine the issue it holds. Only a label-identified gate is ever repaired.
- `<repair-ceiling>=5` edge removals per run. Reaching it stops the pass and reports the remainder rather than working through a whole tracker unattended in one pass.

REPAIR SEQUENCE, per undeclared edge, in this order. Everything that must survive a crash is written BEFORE the destructive step, the quarantine included:

1. Write the removal record on the gate, in TWO parts:
   - The record itself goes in a note: `bd update <gate-id> --append-notes="edge removed: <gate-id> blocks <dep-id> | <edge-type> | census <census-run> | <iso-time> | labels observed: <labels>"`.
   - The index goes in metadata: read the gate's current `backlog_loop_edge_removed`, append `<dep-id>` to that space-separated list, and write the whole value back. `--set-metadata` REPLACES a value. The list is what sequence item 2's skip test reads.
2. Read the gate's acceptance criteria, append the release condition to what is already there, and write the whole field back. `bd update --acceptance` REPLACES, there is no append form, and unlike description and design there is no `--acceptance-file` either, so the entire field round-trips through one shell argument. Then re-read it and require BOTH: the release condition present in full, and the author's original text still present as an exact substring. Either half missing -> the write did not land: stop this repair, restore nothing else, and report it. Never proceed to the removal on an unverified acceptance write. Skip items 1 and 2 entirely when `<dep-id>` is already in the gate's `backlog_loop_edge_removed` list and the release condition is already in its acceptance; a second run must not duplicate either.
3. Write the same note on the dependent, and append `<gate-id>` to ITS `backlog_loop_edge_removed` list the same way.
4. Quarantine the dependent: `bd update <dep-id> --set-metadata backlog_loop_quarantine="census <census-run> | <iso-time>"`. A quarantined issue is never admitted to a batch, by any run, and CENSUS files it under its own category so it leaves the loop-responsible set entirely.
5. `bd dep remove <dep-id> <gate-id>` -- the DEPENDENT first, then what it depends on. That order is not a style choice and getting it wrong is not an error: `bd dep remove <gate-id> <dep-id>` exits 0 and prints `Removed dependency: <gate> no longer depends on <dep>` while the real edge stays exactly where it was. After the command, RE-READ the dependent's `dependencies` array and require `<gate-id>` to be gone; report the repair only on that read-back, never on the command's exit status. This is the irreversible step and it is deliberately last. Re-read the gate's labels immediately before it and abandon this repair if a `hard-blocker` has appeared since enumeration.

CLEARING A QUARANTINE. The operator clears `backlog_loop_quarantine` by hand, or this procedure clears it when the removal has been acknowledged -- meaning the gate's `backlog_loop_edge_ack` metadata holds a space-separated list of dependent ids that includes this one. Nothing in this procedure ever writes that key; like `hard-blocker` it is author-only. Report the exact key and the exact value to append beside every quarantined issue, so the person is never left guessing what "acknowledge" means.

REPAIRED NOTHING ELSE. Every other census finding is reported and left alone -- a gate nested as a child step inside an implementation epic, a gate whose label and title prefix disagree, a dependency cycle, a gate carrying `hard-blocker` and holding work. A declared gate's edge stays, and the report names the declaration as the reason the dependent cannot start. The run can show it changed nothing outside the repairs it reported, labels included.

## OWNER-DECISION ISSUES

Reached only for issues CENSUS classified as neither `human-gate` nor `label-defect` -- see `## HUMAN GATES` for why that order is load-bearing. Applies only to an issue whose `issue_type` is `decision` and whose body says the loop may choose; skip none of those. Any other `decision` issue is a person's question, however it reads: never pick an option for it, never batch it, and open no PR for it. Write it `bd update <id> --status=blocked --unset-metadata backlog_loop_heartbeat --set-metadata backlog_loop_run=<run-id> --set-metadata backlog_loop_cause=needs-person --append-notes="needs-person: the body does not say the loop may choose | <the question>"`, uncharged because no loop-authored work was blocked, read it back, and report it as `needs-person` with its question and options. An issue of any other type is never owner-decision, whatever its body asks. A granted decision always runs solo so one PR carries one decision. Pick your recommended option, preserve any existing design text, append `<decision> | rejected: <alt> | reason: <why>` to the design field through a file, never a shell argument: `bd update --design` replaces the whole field, so read the current design, write it plus the appended line to a file, and run `bd update <id> --design-file <file>`. Read the field back and require the original text as an exact substring and the appended line in full; either missing -> the write did not land, so do not start the batch and report it. Add the `owner-decision` label for the user's audit. Never overwrite an existing design record.

## CONSTRAINTS

Preflight constraints hold on every diff. The applicable quality gate set is green before every PR, no exceptions. Everything written to repo, git, or tracker is English: identifiers, comments, error strings, test names, issue text, commits, PR bodies.

This procedure writes exactly four statuses: `open`, `in_progress`, `blocked`, and `closed`. It never writes `hooked`, `pinned`, or `deferred`. Those three are a person's or a sibling skill's parking decision, and CLASSIFY reads them as one. `in_progress` is written only by `bd update <id> --claim` and by ADOPTION's guarded write.

A batch member this run cannot complete is written `blocked` with a recorded `backlog_loop_cause`, plus the line `## FINAL REPORT` already requires. An open linked PR waiting on checks or mergeability uses `transient:pr-open` and OPEN PR RESUME rechecks it on later runs; a decision that truly requires a person uses `needs-person`. CLASSIFY files a `needs-person` issue as `self-blocked-needs-person`, outside the loop-responsible set; it files a recoverable open PR as `self-blocked-transient`, still in that set until its PR merges, the attempt ceiling is reached, or LINKED PR DISPOSITION sends it to `needs-person`, except that an issue whose open linked PR REPORT lists as awaiting a required approval is reported as awaiting a person and does not hold back the clear verdict. Nothing here decides whether an issue is actionable by reading its body, and nothing invents a fifth status for the case.

## STOP EARLY AND REPORT

Stop only when no legal agent-executable action remains. Before stopping, run CENSUS and distinguish a scoped issue or batch failure from a blocker that prevents every selectable issue from reaching the merge gates. A scoped plan, implementation, review, test, PR, or merge failure is written to its members with the evidence and cause required above, then the loop continues to independent `ready` work. Repeated issue IDs are not re-attempted; they are skipped from selection and their recorded state is reported. Counts of failed batches or merges never substitute for the reachability decision.

Global terminal blockers are: a REQUIRED preflight capability is absent or unauthorized; a required status check has no producer on either CI route; another live backlog-loop invocation owns state; the local default branch contains unoffered commits; required merge-queue semantics cannot be used safely; a required gate or uncovered workflow command cannot execute in the available environment; tracker enumeration or ledger recovery remains incomplete after bounded read retries; owned process or Compose cleanup cannot be proved; the machine guard remains above `2 x <cores>` after reap and recheck; or TRUNK REPAIR proves every path to green gates depends on a person, an external owner, or an external-state change the agent cannot perform. A timed-out or failed merge is terminal only when its diagnosed cause applies to every remaining batch; otherwise keep that PR open, block only its members with the PR URL retained, and continue. Name the exact human action or external change required and why no independent batch can proceed.

## FINAL REPORT

Build it from CENSUS plus the union of `bd list --all --limit 0 --metadata-field backlog_loop_run=<run-id> --json` and the same query for `backlog_loop_census=<census-run>`, plus the touched issues' notes - not from memory and not from all historical closed issues. `--metadata-field` filters on one key=value pair and repeating it narrows rather than widens, so the union is two queries and not one. Scope it to non-closed issues plus this run's own closures. A previous run's block carries a different `<run-id>` and MUST still appear. Both flags are load-bearing: `bd list` hides closed issues unless `--all` is passed and returns at most 50 rows unless `--limit 0` is. Include every decision made on the user's behalf. Report batch composition with its budget and both scoped CI observations (`batch N: <ids> | trunk CI on|off / PR CI on|off | est <n> min | actual <k> files | reaped <n>g/<m>o -> <pr url>`), every re-estimate drop and its reason, every `oversized` anchor, and every batch-level failure. For every PR-CI-off batch, name why no PR check was eligible, state explicitly that no server-side PR verification backed its merge, list the local pre- and post-merge gate set actually run, and repeat the gate-coverage gaps found in preflight. List every pending post-merge CI watch with its PR, merge SHA, first-seen time, workflow URLs, next-poll condition, and owner issue; report a red result and its repair issue or resolution proof.
