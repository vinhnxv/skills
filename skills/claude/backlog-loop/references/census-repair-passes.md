# Census Repair Passes.

This text belongs to this skill's `SKILL.md` and is read in full before it runs.

<!-- body -->
RELEASE GUARD, before REOPEN PASS or PROBATION PASS reopens anything: (a) an issue that records `backlog_loop_pr`, or whose `backlog_loop_branch` has a PR (`gh pr list --head <branch> --state all`), is not reopened here; OPEN PR RESUME and LINKED PR DISPOSITION own it, so no second build or PR is ever created, and the report names the PR. (b) An issue whose `backlog_loop_compose_projects` or `backlog_loop_worktrees` still names a record first runs that record's teardown from its recorded tree through its recorded Docker context, and the exact project must be absent from `docker --context <docker-context> compose ls --all --quiet`; an unproved teardown is reported by project and the issue is not reopened. A delay alone is never proof. (c) The reopen note ends with `last branch <backlog_loop_branch>, head <backlog_loop_head>` read before the write, because the reopen clears those keys and the RETRY BRIEF needs them.

REOPEN PASS. For each `self-blocked-transient` issue, in ascending id order:

- `backlog_loop_attempts` at or above its ceiling (`<attempt-ceiling>=3`, or `<repair-attempt-ceiling>=5` for a trunk-repair member) for any cause, `transient:pr-open` included -> rewrite `backlog_loop_cause=needs-person`, write the ESCALATION DOSSIER below, write `backlog_loop_ceiling` in that same command when the prior cause was `transient:gate-failed`, `transient:review-residual`, or `transient:tool-failure`, name it in the report, and REOPEN PASS never reopens it again: only PROBATION PASS may grant another attempt, and never past the lifetime cap. No cause is exempt from the ceiling, and `backlog_loop_attempts_total` never resets.
- ESCALATION DOSSIER, written once with that rewrite: one `--append-notes` entry that lists, per attempt, the date, the failing command, its exact error, and the `retry-hypothesis` tried; then the strongest remaining suspicion, and the command a person runs to grant one more attempt: the reopen update REOPEN PASS uses, with RELEASE GUARD's note, `--set-metadata backlog_loop_cause=<prior-cause>` and `--set-metadata backlog_loop_attempts=<ceiling-1>`; for an issue that records a PR, the instruction to resume that PR through OPEN PR RESUME instead, because a fresh build would orphan it. Report that command beside the issue. This step never creates an issue and never writes the `human-gate` label, which stays author-only; independent ready work keeps flowing.
- Otherwise prove the recorded cause is gone before touching it. The cause is a recorded value, not a reading of the note: `transient:trunk-moved` is gone when `<remote>/<default>` is currently green under the recorded `backlog_loop_trunk_ci` route (missing -> local clean-tree gate); a PR-head check does not prove trunk health. Exception: a trunk-repair member (metadata `backlog_loop_trunk_repair` set, or it covers a recorded `<trunk-failures>` entry) is exempt from the green-trunk test, because its own repair is what makes trunk green and requiring green first would deadlock it. It is gone when no live run owns the issue and `backlog_loop_attempts` is below `<repair-attempt-ceiling>`; reopen it and let TRUNK REPAIR select it with the complete repair set. The legacy `transient:merge-precondition` is gone when the recorded PR is `CLOSED` and no PR is open on the recorded branch. `transient:gate-failed`, `transient:review-residual`, and `transient:tool-failure` are gone when `backlog_loop_attempts` is below the ceiling: the failure is a defect this loop can fix, so reopen it, and the next claim reads the recorded failing command and error from the notes and reproduces it first. A `transient:tool-failure` waits `<tool-retry-delay>=15m` after its block note first, so a flaky service is not hit again at once. `transient:decision-recorded` is gone when `backlog_loop_attempts` is below the ceiling and the issue's design field holds, as an exact substring read from `bd show <id> --json`, the entry its block note quotes after `design entry:`; it waits for no cooldown, because nothing outside the issue changed. A block note that quotes no entry, or an entry the design field no longer holds, is not proof: rewrite `backlog_loop_cause=needs-person` and name the missing entry. Trunk-repair members take this path too; never leave one at `needs-person` below the ceiling. `transient:pr-open` is handled by OPEN PR RESUME, never by reopening this issue; skip it in this pass except for the ceiling above. A `MERGED` PR is NOT that proof, even though a merged PR is also a closed one: the work is already on trunk, so reopening rebuilds shipped code. Read the PR's state explicitly and require `CLOSED`; on `MERGED`, leave the issue for LINKED PR DISPOSITION's `MERGED` row, which verifies and closes it. A bare `transient` with no subtype, or any cause with no proof the census can evaluate on its own, is not a transient cause at all: record it `needs-person` rather than leaving it to expire on a condition nothing can satisfy.
- Proven -> one atomic update, following the reclaim shape: `bd update <id> --status=open --assignee="" --unset-metadata backlog_loop_run --append-notes="reopened by census <census-run>: <cause> no longer holds"`, plus unsetting every other RUN-class and FORGE-LINK-class key (KEY CLASSES). DURABLE keys are deliberately NOT cleared: the attempt count is what bounds the cycle.
- A legacy block whose note begins `post-merge verification failed:` (an earlier form of this procedure wrote it; nothing writes it now) is never reopened, whatever trunk currently looks like. Its code is already on trunk and its phase is already `merged`; the proven-merge rule in THE RUN LEDGER says that work is finished, not rebuilt. LINKED PR DISPOSITION's `MERGED` row returns its member to `in_progress` at `merged`, so I7's CI watch or repair disposition takes it; never rebuild its merged code.

PROBATION PASS. A ceiling is a pause, not a verdict, when the work failed for a reason a later state can change. For each `self-blocked-needs-person` issue that carries `backlog_loop_ceiling` (`<iso> | <trunk-sha> | <skill-digest> | <prior-cause>`, written only when the ceiling rule rewrote a `transient:gate-failed`, `transient:review-residual`, or `transient:tool-failure` cause), in ascending id order:

- Skip it when `backlog_loop_ceiling` begins `consumed`, or when the ESCALATION DOSSIER is not the newest note on the issue: a later note means a person or another pass has acted, and the old escalation no longer describes the issue.
- Skip it when `backlog_loop_attempts_total` is at or above `<lifetime-attempt-cap>=9`; that count never resets, and the issue stays `needs-person` for good. An issue with no `backlog_loop_attempts_total` counts as `backlog_loop_attempts`.
- Skip it until `<probation-cooldown>=24h` has passed since the recorded time (`2h` for a member stamped `backlog_loop_trunk_repair`, because a red trunk stops every merge).
- Skip it while `<remote>/<default>` still resolves to the recorded `<trunk-sha>` AND the digest of the running `SKILL.md` equals the recorded `<skill-digest>`: nothing has changed that could alter the outcome, so another attempt would repeat the last one.
- Otherwise, once RELEASE GUARD passes, grant exactly one probation attempt in one atomic update: `bd update <id> --status=open --assignee="" --unset-metadata backlog_loop_run --set-metadata backlog_loop_attempts=<ceiling minus 1> --set-metadata backlog_loop_ceiling="consumed | <iso>" --set-metadata backlog_loop_cause=<prior-cause> --append-notes="probation by census <census-run>: trunk or skill changed since <iso>"`, plus unsetting every other RUN-class and FORGE-LINK-class key (KEY CLASSES). The ceiling is `<attempt-ceiling>`, or `<repair-attempt-ceiling>` for a trunk-repair member. The attempt it grants is charged like any other, and the grant consumes the record so the same change never grants twice, a later ceiling overwrites it with a fresh stamp, so the cycle is bounded by the lifetime cap and never by a reset. Report every probation with its issue and the changed condition.

TRIAGE PASS. Issues parked before the transient causes existed carry `needs-person` for a reason the loop can retry. For each `self-blocked-needs-person` issue with `backlog_loop_attempts` below its ceiling (absent counts as 0), no `backlog_loop_ceiling`, and no `backlog_loop_triaged`, require the newest note on the issue to be a `pipeline blocked:` note (a later note of any kind, a person's close or park included, leaves the issue untouched), and classify that note by its reason text alone: a `gate failed:` prefix, or a reason that names a failed required command or test, is `transient:gate-failed`; a `review residual:` prefix, or a reason that names unapplied or residual review findings and meets every condition of `transient:review-residual` in I7's list, is `transient:review-residual`; a `tool failure:` prefix, or a reason naming a `failed`, `degraded`, or `skipped` review status, a malformed return, a timeout, or an unproved teardown, is `transient:tool-failure`. Anything else, and every note that names a person's decision, a credential, a draft, a retargeted or closed PR, or a moved head, is left exactly as it is. Rewrite the cause and stamp `backlog_loop_triaged=<census-run>` in one `bd update`, and never write `--status`: REOPEN PASS reopens the issue on its own proof. Stamp each issue once, so a triage that was wrong is never repeated. `<triage-ceiling>=10` rewrites per run; reaching it stops the pass and reports the remainder, so a large legacy backlog drains over several runs instead of reopening at once. The same pass retires one denial this procedure no longer issues: a `self-blocked-needs-person` issue whose `issue_type` is `decision`, with `backlog_loop_attempts` below its ceiling, no `backlog_loop_ceiling`, and no `backlog_loop_triaged`, and whose newest note begins `needs-person: the body does not say the loop may choose`, is reopened with the reopen shape REOPEN PASS uses and `--append-notes="reopened by census <census-run>: owner-decision denial retired"`, stamping `backlog_loop_triaged=<census-run>` in that same command; a later note of any kind leaves it untouched, and each reopen counts against `<triage-ceiling>`.

EXTERNAL LEASE PASS. An `external-wip` issue is never stolen on the loop's judgment, but the tracker keeps a lease for every claim and `bd reclaim` is the tracker's own reaper, so a claim whose lease expired is the tracker's record that nobody holds it. This is a mutation pass under WRITE GATE: it is skipped entirely when the run is a diagnostic run or any other run of this procedure holds a live heartbeat. For each `external-wip` issue, in ascending id order, skip it and report it as `held` when an open PR names the issue in its title, body, or head branch; otherwise run `bd reclaim --id <id>` with the tracker's default grace window, read the issue back, and report it as `reclaimed` only when the read-back shows `status=open` and no assignee. Any other read-back leaves the issue `external-wip` and reports `held`. Never pass `--force`, `--any-replica`, or `--older-than`, and never write `bd update --assignee` on this path: a lease granted by another replica is skipped by the tracker, and a claim with no lease is not reclaimed. Stamp `backlog_loop_census=<census-run>` on a reclaimed issue in a separate `bd update` after the read-back shows `open`. A diagnostic run prints `would evaluate: bd reclaim --id <id>` for each such issue and writes nothing.

ORDER AND REFRESH. The passes run in this order: REOPEN PASS, PROBATION PASS, TRIAGE PASS, EXTERNAL LEASE PASS. After the last one, re-run CLASSIFY and the loop-responsible count over every issue any of them wrote, and only then print REPORT, apply `## ITERATION` I2, or select a batch. A count taken before those writes is stale and never decides that the backlog is clear.

Stamp `backlog_loop_census=<census-run>` on every issue this section writes to, as part of that same write rather than as a second command.
