# Follow-Up Filing.

This text belongs to this skill's `SKILL.md` and is read in full before it runs.

<!-- body -->
   FOLLOW-UP FILING. This is the first thing step 7 does once I6 has proven the merge, before it records `backlog_loop_postmerge_ci`, because a crash after that point resumes at `merged` and finds the same note. Skip it when the anchor already carries a `followup-filed v1` note or carries no `followup-candidates v1` note. Read the candidates in the newest `followup-candidates v1` note only, because an earlier note comes from a review round that a retry superseded, query `bd list --limit 0 --has-metadata-key backlog_loop_followup_key --json` once, and drop every candidate whose fingerprint is already the `backlog_loop_followup_key` of a non-closed issue, recording that issue's id. Order the rest by severity and then fingerprint, and file at most `<followup-per-batch>=8` of them per batch and at most `<followup-per-run>=25` in the whole invocation, counted in a running total the invocation keeps. For each, write the body to a file and the metadata JSON to a second file with a JSON encoder, never by interpolating review text into a shell string, then run `bd create "<English title>" --id <prefix>-f<first 8 hex of sha256(fingerprint)> --type <bug|task> --priority <P2|P3|P4> --labels tech-debt --estimate <minutes> --acceptance "<criteria>" --body-file <body-file> --metadata @<metadata-file> --silent`, where `<prefix>` is `bd config get issue_prefix` and the metadata object holds `backlog_loop_followup_key` set to the fingerprint and `backlog_loop_followup_of` set to the member ids; a refused duplicate id is a match, so read that issue and move on. The type is `bug` for a `findings` or `pre_existing_findings` candidate and `task` for the rest. The priority is P2 for a `findings` candidate of severity P0, P1, or P2, P3 for any other `findings` candidate and for every `pre_existing_findings` candidate, and P4 for `residual_risks` and `testing_gaps`; it is never above P2, because a finding that serious would have been actionable and gated the merge. The body states the problem from `why_it_matters`, the `file:line`, the `suggested_fix`, the batch members, and the review `artifact_path`; the acceptance criteria name the cited behavior and an independent check that fails before the fix and passes after; the estimate follows the BATCH BUDGET rubric. A follow-up is an ordinary open issue: never write the `human-gate` label or the other author-only label that `## HUMAN GATES` names, a status, or a dependency that blocks anything. Then run `bd dep add <follow-up-id> <anchor-id> --type discovered-from`, and read every created issue back. Candidates beyond `<followup-per-batch>` become one rollup issue, created the same way with the fingerprint `rollup|<anchor-id>|<merge-sha>`, type `task`, and priority P4, whose body lists them; when `<followup-per-run>` is already reached they are listed in FINAL REPORT only. Only after every read-back succeeded, append `followup-filed v1 | created <n> | duplicate <m> | overflow <k>` to the anchor. A failed create or read-back stops this paragraph without failing the member: report it, leave the filed note unwritten, and the next poll retries the rest, deduplicated.
