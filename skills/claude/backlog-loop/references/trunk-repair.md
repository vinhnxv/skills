# Trunk Repair.

This text belongs to this skill's `SKILL.md` and is read in full before it runs.

<!-- body -->
   FLAKE CHECK. A recorded `failed` exact-merge result, or a red trunk failure, whose newest run on the same SHA is green, or whose red workflow is not reproduced at once, is not yet a code failure. Before TRUNK REPAIR claims it, run the exact failed command through CLEAN-TREE GATE RUN at that SHA `<flake-rerun>=3` times in a row. Any red run is a real failure and enters TRUNK REPAIR with that run's evidence. Three green runs record `backlog_loop_postmerge_ci=<merge-sha> | <first-seen-utc> | intermittent` and let the member finish I7's close with `intermittent` in its close reason, but only once every other I7 condition holds too: every other expected exact-merge workflow is terminal and green, the applicable local gate set is green, and every worktree and Compose record is retired. The hold on ordinary merges lifts only when the newest run of every workflow on current trunk is green too. The check never discards the evidence: run the TRUNK REPAIR coverage search, and when no non-closed issue covers the failure, create one agent-executable P1 bug (not P0) titled `Stabilize flaky:` with the failing command, the red run URLs, and the green rerun count, plus metadata `backlog_loop_trunk_repair=<trunk-sha>`; a covering issue that already exists is reused and its priority is not raised. Its fix must remove the nondeterminism, never weaken the assertion.

   TRUNK REPAIR. Record `<trunk-failures>` as the exact trunk SHA plus every failing workflow, job, command, test, and concise error available from the CI log or local gate. Build it from the COMPLETE failing-step set of the exact-SHA gate log or CI run: enumerate every failing target (every red step of `make check`, every red job of the run) before choosing members, because a read that stops at the first failure is a defect. When the gate stops at its first failure, run the remaining gate stages separately at that SHA until every stage has a result. Run CENSUS before deciding to stop, then inspect every non-closed non-epic issue for explicit coverage of those failures in its title, description, acceptance criteria, design, or notes. Reuse matching work rather than duplicate it. A matching `ready` issue is a repair member; a matching issue owned by another live run or external assignee is not stolen. If any recorded failure has no matching issue, create one agent-executable P0 bug with `bd create`, an English title beginning `Restore trunk:`, the observed evidence in its description, the requirement that the exact failed check and the full gate set pass in its acceptance criteria, a rubric-derived estimate, and metadata `backlog_loop_trunk_repair=<trunk-sha>`. Never create or label it as a human gate.

   The complete repair-member set is forced into one repair batch before normal ANCHOR selection, because the final branch must make every currently failing gate green. It runs solo from unrelated backlog work, may exceed TARGET, CEILING, and CONCERNS when the observed failures require an atomic repair, and its plan and diff are limited to causes of `<trunk-failures>` plus necessary regression coverage. The red base result is the reproduction: under `<trunk-ci>=on`, the exact-SHA CI logs supply it; under `<trunk-ci>=off`, CLEAN-TREE GATE RUN must reproduce it. Every base gate outside `<trunk-failures>` must remain green. The branch head must pass the exact failed checks and the complete current quality-gate set before shipping; then the normal PR, CI, review, and merge protections apply unchanged.

   Stamp every selected repair member with `backlog_loop_trunk_repair=<trunk-sha>` before CLAIM. If a matching repair issue is externally owned, parked by a person, gated on unavailable human input, or already exhausted at `needs-person`, do not create a duplicate to evade that ownership. Report it as the global blocker. Stop only when at least one recorded trunk failure has no agent-controlled retry or repair, and the requirement that the complete gate set turn green means no batch can legally merge until a person, external owner, or external state resolves it. After a repair merge, re-probe the new exact trunk SHA and finish any current-run `merged` members waiting on post-merge verification before selecting ordinary work.

   RESOLVED REPAIR. A repair member can become moot because someone else fixed trunk. Before forcing a repair batch, test every non-closed issue whose title begins `Restore trunk:` and that is stamped `backlog_loop_trunk_repair=<stamp-sha>`, whose acceptance criteria require nothing beyond the exact failed checks and the full gate set, and that no live run owns (a reused issue with any other criterion, and every `Stabilize flaky:` issue, is never tested here, because green commands do not prove its remaining work), that records no `backlog_loop_pr` and no PR on its branch, and whose compose and worktree records are retired (RELEASE GUARD's conditions): it is resolved only when `<remote>/<default>` is a descendant of `<stamp-sha>` and not equal to it, the exact failed commands of its recorded failures each pass 3 runs in a row through CLEAN-TREE GATE RUN at the current trunk SHA, and the complete current gate set is green there. Then append a note naming the trunk SHA, the commit range `<stamp-sha>..<trunk-sha>`, at least one commit in that range that changes a file one of the failing commands exercises (a range with no such commit is no proof), and each command with its 3 green results, and close it with `bd close <id> --reason="resolved on trunk <trunk-sha> by a later commit; no code change needed | <evidence>"`. A trunk equal to `<stamp-sha>` whose commands now pass is intermittent and goes through FLAKE CHECK, never this rule; any red run, or an issue that covers failures still red, stays a repair member; this rule never closes an issue whose commands it did not run. It is a mutation under WRITE GATE: a diagnostic run prints `would evaluate: close <id> as resolved` and writes nothing.
