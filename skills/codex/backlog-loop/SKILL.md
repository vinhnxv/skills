Clear this repo's issue backlog autonomously, one batch at a time, until CENSUS below shows no issue left in a category this loop is responsible for. An empty `bd ready` list is never that proof. Never ask the user anything; when a choice arises take your recommended option and record it.

A batch is 1..N sibling issues sized against a complexity budget. One batch = one plan = one branch = one PR = one merge.

This procedure is the outer loop and shipping authority. For every batch, read the available `compound-engineering:lfg` skill and drive its current stages through the documented `ce-plan`, `ce-work`, review, browser-test, ship, and babysit seams. Do not invoke LFG as an indivisible child. Resolve every named child skill against the host's available-skills list and use host-native invocation; never guess slash or dollar syntax. Never bypass a child skill's applicable gates.

Why each rule exists, and the incidents behind it, is in this skill's `references/rationale.md` (not LFG's `references/`), keyed by section heading. It adds no rule; this file is complete without it. Steps are cited `I<n>` for the numbered ITERATION steps and `P<n>` for the numbered PIPELINE steps inside I5; where an older sentence says a bare `step N`, read it the same way: a PIPELINE step inside the PIPELINE list, an ITERATION step elsewhere, and "the blocked path in step 7" always means I7.

## CLEAN-TREE GATE RUN

Every gate whose result authorizes a merge -- the I1 trunk gate, the P6 pre-PR gate, and I7 post-merge verification -- runs against a throwaway worktree at an exact commit, never in the working tree.



- `<clean-tree>` is `<worktree-root>/<sha>`, where `<worktree-root>` is a single run-owned directory outside every worktree of this repository, named after `<run-id>`, contains no whitespace, and is recorded once in the ledger as `backlog_loop_worktrees`. `git worktree add --detach <clean-tree> <sha>`. When any gate or application command may invoke Docker Compose, give this tree one unique `<compose-project>` derived from the run id and SHA, restricted to Compose's lowercase project-name alphabet. Resolve `<docker-context>` with `docker context show`, require it to contain neither whitespace nor `@`, and append `<compose-project>@<docker-context>@<clean-tree>` to `backlog_loop_compose_projects` on every batch member before starting the command. Pass the exact project through `COMPOSE_PROJECT_NAME`; invoke Compose through `docker --context <docker-context> compose`; and require the command to use the Compose configuration resolved from `<clean-tree>`. A command that needs `-f`/`--file`, `--project-directory`, `--env-file`, `-p`/`--project-name`, an unrecorded `DOCKER_HOST`, or a different Docker context has no replayable cleanup record and blocks before start. Never reuse the repository's default Compose project.
- `<worktree-root>` lies outside every worktree of this repository: its path is neither inside nor above any path `git worktree list --porcelain` names, and not inside `git rev-parse --git-common-dir`. Every worktree this loop creates sits directly under it. Only a path under it is ever removed, with `git worktree remove --force <path>`, which also clears a registration whose directory is already gone; nothing here prunes repository-wide, because a prune also drops the registration of any worktree of the operator whose directory is temporarily missing.
- `<trunk-tree>` is `<worktree-root>/trunk`, the run-owned worktree that holds the trunk checkout and every batch, TRUNK REPAIR included. I1 creates it with `git worktree add --detach <trunk-tree> <remote>/<default>` when it is absent and otherwise moves it with `git -C <trunk-tree> switch --detach <remote>/<default>`. It is detached and holds no branch; the work branch `ce-work` cuts there starts from `<batch-base-sha>`. ITERATION steps 3 through 7 run every child skill with `<trunk-tree>` as the working directory, never `<invoking-worktree>`.
- If the gate set needs installed dependencies, run the repo's documented install or bootstrap command inside every run-owned worktree a child skill or gate runs in -- `<trunk-tree>`, `pr-<number>`, and `<clean-tree>` -- before the first one runs there, preferring its frozen/locked form. Then require `git status --porcelain` in that worktree to report no change to a tracked file. Any tracked change -> the gate has not passed. A gate that cannot execute there has not passed either, and neither may be recorded as green.
- Run the gates there under the same process-hygiene rules, including the run token and `<owned-pgids>`. A command that may invoke Compose runs from `<clean-tree>` with `COMPOSE_PROJECT_NAME=<compose-project>` inside a shell that installs its cleanup trap BEFORE the command starts. The `EXIT` trap captures the command status, disables its own signal traps, runs `docker --context <docker-context> compose -p <compose-project> down --remove-orphans`, and requires the exact project name to be absent from `docker --context <docker-context> compose ls --all --quiet`. Cleanup success returns the original command status. Cleanup failure returns non-zero even when the command succeeded, while an already non-zero command keeps its original status, so every failure blocks; `HUP`, `INT`, and `TERM` traps exit non-zero so the `EXIT` trap still runs. A trailing `docker compose down` line is not equivalent.
- Before removing a Compose-owning worktree on either the green or red path, repeat that teardown idempotently from `<clean-tree>` with the recorded context and require the exact project name to be absent from `docker --context <docker-context> compose ls --all --quiet`. Only then retire that `<compose-project>@<docker-context>@<clean-tree>` record from every batch member, and run `git worktree remove --force <clean-tree>`, which also clears the registration of a tree whose directory is already gone. A failed teardown keeps the worktree and its ledger record for RECOVERY and blocks the batch.
- A gate that ends in a DEADLINE has not failed on the code. Record the command and the elapsed time, wait for the I1 machine guard to be green, and rerun that gate once in a fresh `<clean-tree>` at the exact same SHA with the deadline doubled and capped at `<gate-timeout-cap>`. A green rerun is the gate result. A second DEADLINE, or a first one when `<gate-timeout>` is already at or above `<gate-timeout-cap>`, ends the gate as `transient:tool-failure` with the reason `tool failure: gate deadline`, and the note carries the command, both deadlines, and the observed elapsed time. A DEADLINE is never `transient:gate-failed`.

Tag every claimed member with `bd update <id> --set-metadata backlog_loop_run=<run-id>`; remove that metadata from members dropped before implementation.

Do not resolve a plans directory here. `ce-plan`, under LFG's `plan-brief.md` contract, resolves its own artifact root and reports the path it wrote; I5 uses that reported path and nothing else.

## STATE

State lives in the tracker. Re-read `bd ready --json --limit 0` every iteration; never work from a remembered list. Every `bd ready` call carries `--limit 0`: without it the tracker returns at most 100 rows, so a larger backlog reads as a smaller one. Also inspect non-epic `in_progress` issues and split them by the PRESENCE of `backlog_loop_run` metadata, never by its value.

- Marker present: an earlier run of this procedure claimed it and did not finish. Recover it through THE RUN LEDGER below.
- Marker absent: externally owned. Never steal it on the loop's own judgment; the only release is the tracker's lease through CENSUS's EXTERNAL LEASE PASS. If no ready work exists and one of these remains, stop and report that the backlog is not clear.

That split is an ownership test and CENSUS extends it into a full accounting of every non-closed issue. A `needs-person` cause alone on a blocked issue marks this loop's own release of a person-closed PR, even after its RUN keys are unset. Read CENSUS before deciding that anything is finished.

HEARTBEAT REFRESHER. The first time an iteration stamps a `live` heartbeat (CLAIM or ADOPTION), launch one refresher under process hygiene: `perl -e 'setpgrp(0,0); exec @ARGV' -- sh -c 'n=0; while [ "$n" -lt 36 ]; do <refresh> || break; n=$((n+1)); sleep 600; done'`, with `BACKLOG_LOOP_RUN=<run-id>` and `BACKLOG_LOOP_ROLE=refresher` exported and its leader PID appended to `<owned-pgids>`. It is the one command here with no `<gate-timeout>`, so its lifetime is bounded another way: 36 ticks (6 hours), and it stops at the first `<refresh>` that fails or that finds no `in_progress` issue carrying `backlog_loop_run=<run-id>`. A run that died without REAP therefore leaves no refresher alive after 6 hours. A stage boundary that finds the refresher's group gone launches it again, so a live run is never left without one. I8 REAP ends it with the iteration's other groups. Every 10 minutes it refreshes every `in_progress` issue carrying `backlog_loop_run=<run-id>`: it writes `backlog_loop_heartbeat="<iso> | live"` and runs `bd heartbeat <id>`, which renews the claim lease and refuses a parked issue. Run the same refresh yourself at every pipeline stage boundary, I5 through I7.

ADOPTION. A parked PR is adopted by one write, guarded so two invocations cannot both take it: `bd update <id> --if-status blocked --status=in_progress --assignee <actor> --set-metadata backlog_loop_run=<run-id> --set-metadata backlog_loop_heartbeat="<iso> | live"`. The write stamps the RUN-class run and heartbeat, so the adopted issue classifies as `claimed-this-run`. Read the issue back and require status `in_progress`, assignee `<actor>`, and `backlog_loop_run=<run-id>`. Any nonzero exit with an unchanged read-back means another invocation adopted it first: skip the issue and write nothing. Exit 13 is the status guard, but a second adopter that names its own assignee is refused with exit 1 before the guard is reached, so never read the exit code alone. Adopt a PR's members in ascending id order; losing the first member skips the PR this iteration. After a won adoption run `bd heartbeat <id>` and start the HEARTBEAT REFRESHER when this iteration has none. A member still `in_progress` under a dead run (RECOVERY) is parked first, never adopted in place: re-read its status and `backlog_loop_run`, skip it when either changed, then one `bd update <id> --if-status in_progress --status=blocked --unset-metadata backlog_loop_heartbeat --set-metadata backlog_loop_cause=transient:pr-open`, uncharged, and adopt it with the write above. Exit 13 means another invocation moved the member first: skip it and write nothing.

Every write that sets `blocked`, in the table above or anywhere below, carries `--unset-metadata backlog_loop_heartbeat` in that same command.

CHARGING. A charge is `backlog_loop_attempts` and `backlog_loop_attempts_total` each set to its current value plus one (an absent total starts from the attempts value), read back after the write. Charged: a pipeline block on work this loop authored, a guarded-merge refusal after such work, and each row above marked charged. Never charged: a poll, a pending check, a trunk move at P6 or in the base-behind row, waiting on a required approval, an interruption park in RECOVERY, a `transient:scope-incomplete` block (the scoping failed, not the work), and every row that goes straight to `needs-person`. The ceiling `<attempt-ceiling>=3` bounds one issue across its whole life for every cause, `transient:pr-open` included, and REOPEN PASS enforces it. PROBATION PASS may grant one further attempt after a ceiling, and `<lifetime-attempt-cap>=9` charges bound the issue absolutely. A member stamped `backlog_loop_trunk_repair` has the higher ceiling `<repair-attempt-ceiling>=5` instead, because a red trunk stops every merge and one more diagnosed attempt costs less than the stall. There is no run-level counter: a scoped PR never stops independent work.

Never close a PR automatically. A PR this procedure cannot land stays open. Parking it means keeping its branch and `backlog_loop_pr` ledger link, setting its issue to `blocked` with `backlog_loop_cause=transient:pr-open`, and reporting the exact pending gate or review. Do not reclaim or rebuild that issue while its PR is open. Every later loop invocation rechecks that PR through OPEN PR RESUME, which applies the table after refreshing its head, base, review, and verification state. Only a row that needs a person's action becomes `needs-person`. Reclaim only when no PR exists for the recorded branch.

Reclaim means `bd update <id> --status=open --assignee="" --unset-metadata backlog_loop_run --append-notes="reclaimed from interrupted run <old-run-id> at phase <phase>"`, plus unsetting the rest of the RUN class and the FORGE-LINK class (KEY CLASSES), returning the issue to `bd ready`. No DURABLE key is unset: the attempt count, cause, quarantine, edge records, and trunk-repair mark outlive every reclaim.

Before any of that, and only after LIVENESS has proved the old run is gone, reap its escaped processes by its `<old-run-id>` token exactly as I8 does. Then read every `backlog_loop_compose_projects` record, run the CLEAN-TREE teardown from its recorded worktree through its recorded Docker context, and require the project absent from `docker --context <docker-context> compose ls --all --quiet` before removing that worktree. A missing tree or failed teardown is a recovery blocker and is reported with the exact project name; never delete the remaining worktree root and strand the stack. After every recorded project is absent, remove every worktree registered under `backlog_loop_worktrees` with `git worktree remove --force <path>`, which also clears a registration whose directory is already gone, then delete the emptied directory with `rmdir`; never prune repository-wide, so an interrupted run's worktrees and their installed dependencies do not accumulate on disk until a later gate cannot create one.

There is deliberately no run-global failed-batch or failed-merge counter. `<owned-pgids>` is in-memory by design, which is why every command also carries the run token - the token is what makes a dead run's processes findable when its PID list is gone. A failed or blocked attempted batch is marked `blocked`, so it cannot be selected again silently. An open linked PR is the exception: OPEN PR RESUME rechecks the existing PR without rebuilding it or charging another attempt for each poll. `backlog_loop_attempts` bounds one ISSUE across its whole life. CI is batch-scoped and re-resolved from the exact current trunk SHA every iteration; it may change in either direction.

## CENSUS

One classification pass over the whole tracker, written once and read by both entry points. Both evaluate the same recorded fields under the same stated precedence, so a category difference between a diagnostic run and a loop run over an unchanged backlog is a defect -- in this section, the fixture, or the tracker -- and never a permitted outcome. The loop runs it at the termination decision; the companion census prompt runs it alone. Nothing below infers termination from an empty `bd ready` list.

Choose a `<census-run>` token the same way as `<run-id>`.

ENUMERATE. `bd list --all --limit 0 --include-gates --json`, then discard `status=closed` and `issue_type=epic` rows. Every flag is load-bearing: `--limit 0` lifts the 50-row cap, `--include-gates` adds native gate issues, `--all` adds `pinned` issues, and the closed rows it returns are discarded in the query. Do NOT pass `--include-infra` or `--include-templates`: agent, role, message, and template beads are not work, have no category below, and would make the exhaustiveness claim false. Say so on the census header line, so an operator reading a count knows what it counted.

`bd ready --explain --json --limit 0` is the AUTHORITY for the dependency question -- which issues are dependency-blocked, and by what -- and not merely a source of blocker names. Do not re-derive it from edges. Count its rows: the `ready` and `blocked` arrays must hold `summary.total_ready` and `summary.total_blocked` rows, and a shortfall is a truncated read, so name the gap and retry as ACCOUNT FOR THE COUNT does.

That explanation covers OPEN issues only. A `blocked` issue appears in neither of its buckets, so every category below that turns on `status` is read from the issue's own stored status.

METADATA IS NOT RELIED ON IN THE ENUMERATION. Whether `bd list --json` carries a `metadata` object or a `dependencies` array depends on the `bd` version: 1.3.0 returns `metadata` on a row that has any and `dependency_count`, but no `dependencies` array to resolve it with. So the marker-bearing rows below are answered by one `bd list --has-metadata-key <key> --json` per marker key -- `backlog_loop_run`, `backlog_loop_cause`, `backlog_loop_quarantine`, `backlog_loop_heartbeat`, `backlog_loop_census_heartbeat` -- intersected with the enumeration.

BACKFILL, once per issue, BEFORE the precedence walk below. A `blocked` issue carrying `backlog_loop_run` but no `backlog_loop_cause` predates this section: it was written by an earlier form of the procedure that recorded only a note. It covers only blocks that already carry a marker; a block with no marker at all is older still, and row 13 handles it without writing anything.

- The note text is not in the enumeration output, so read it with one `bd show <id> --json` per affected issue. That is the one place a per-issue query is allowed, and it is bounded twice over: only `blocked` marker-bearing issues with no cause qualify, and an issue that has a cause key is never re-read.
- Classify it with I7's cause list only: a note beginning `merge blocked; PR remains open:` backfills as `transient:pr-open`, a `pipeline blocked:` note whose reason says trunk moved as `transient:trunk-moved`, a `pipeline blocked:` note whose reason begins `gate failed:` as `transient:gate-failed`, a `pipeline blocked:` note whose reason begins `review residual:` as `transient:review-residual`, a `pipeline blocked:` note whose reason begins `tool failure:` as `transient:tool-failure`, a `pipeline blocked:` note whose reason begins `decision recorded:` as `transient:decision-recorded`, a `pipeline blocked:` note whose reason begins `scope incomplete:` as `transient:scope-incomplete`, and every other note, including the legacy prefix `post-merge verification failed:` that nothing writes now, as `needs-person`.
- Derive the cause in BOTH modes; PERSIST it only when the WRITE GATE below allows. A diagnostic run classifies on the derived value and writes nothing, which is what lets `--readonly` hold. Persisting means `backlog_loop_cause=<derived>` plus `backlog_loop_attempts=1`, except for `transient:scope-incomplete`, which is uncharged: persist its cause alone and keep any existing count.

An `abandoned-claim` is never selected directly. It is this procedure's own wreckage and it goes through THE RUN LEDGER's RECOVERY, which reads `backlog_loop_phase` and decides per phase whether to reclaim, adopt the existing PR, or leave it; only what recovery returns to `open` can be picked in a later iteration.

Two different rules govern the marker. `## STATE`'s rule -- split by the PRESENCE of `backlog_loop_run`, never its value -- decides ownership: present means this procedure's own work, recoverable through THE RUN LEDGER; absent means externally owned and never to be stolen. Rows 4, 8, and 12 are not an ownership question but a liveness one, and they are the ONLY place the marker's value is read, always together with `backlog_loop_heartbeat` under the liveness test. A stale marker with a dead heartbeat therefore still classifies as this procedure's own wreckage -- as row 12 for an unfinished claim, as rows 6 and 7 for a block -- exactly as `## STATE` requires.

LOOP-RESPONSIBLE SET. Exactly five categories are the loop's to clear: `ready`, `claimed-this-run`, `abandoned-claim`, `self-blocked-transient`, and a `dep-blocked` issue whose blocker is itself in one of those. An issue whose open linked PR REPORT lists as awaiting a required approval is reported as awaiting a person and does not hold back the clear verdict. Everything else is somebody's or something else's. `quarantined`, `legacy-blocked`, and `self-blocked-needs-person` are deliberately NOT in the set, because they wait on a person. The backlog is clear when no issue sits in that set -- never because `bd ready` came back empty.

Walking `dep-blocked` transitively meets the cycles this procedure reports and never repairs, so the walk carries a visited set, counts each issue at most once, and treats a repeat visit as the end of that branch plus a reported cycle. Walk the `blocked_by` lists in the `bd ready --explain --json --limit 0` output already taken above, which reports its own cycle count; the enumeration carries no edges to walk.

DIAGNOSTIC RUN. Choose a `<run-id>` the same way an ordinary run does even though nothing will be claimed under it, so rows 4, 8, and 12 have a token to compare against. Either way print one line per member - `<id> | <title> | <url> | merged|blocked` - plus one `batch: <id>,<id>,... | est <n> min | actual <k> files` line.

8. **REAP.** Runs at the end of every iteration - merged, blocked, or stopped early - before I1 of the next batch and before any early-stop report returns.
   - For every `<pgid>` in `<owned-pgids>` still listed by `ps -Ao pgid=`: first re-prove ownership by requiring some current member of that group to carry this run's `BACKLOG_LOOP_RUN` token. Proven -> `kill -TERM -<pgid>`, wait 5s, then `kill -KILL -<pgid>` if it survives. Not proven -> report it, never signal it. Kill the group, never the leader alone. On `<platform>` `windows-native`, WINDOWS NATIVE PROBES replaces the POSIX commands in this step.
   - For every port in `<owned-ports>`, list its listeners with `lsof -i :<port> -sTCP:LISTEN -t`, take each listener's process group, and treat that group exactly like a `<pgid>` above: proven by this run's token -> TERM, then KILL after 5s; not proven -> report it, never signal it. This is how the dev server `ce-test-browser` left running is stopped, and its log is `/tmp/dev-server-<port>.log`. On `<platform>` `windows-native`, WINDOWS NATIVE PROBES replaces the POSIX commands in this step.
   - Then sweep only what this run provably owns: processes whose environment carries `BACKLOG_LOOP_RUN=<run-id>`, read with the platform's environment-listing form of `ps`. TERM, then KILL after 5s. For every `backlog_loop_compose_projects` record, run the CLEAN-TREE teardown from its recorded tree through its recorded Docker context and require the exact project absent from `docker --context <docker-context> compose ls --all --quiet`; only then remove that `<clean-tree>` worktree. If teardown cannot be proved, keep the tree and record, report the exact project, and take the blocked path instead of leaking it behind successful cleanup. After those records are retired, remove every other run-owned worktree -- `<trunk-tree>`, a `<clean-tree>`, or a `pr-<number>` worktree -- with `git worktree remove --force <path>`, and only for a path under `<worktree-root>` that `git worktree list --porcelain` registers; a worktree outside `<worktree-root>` is never removed, whoever created it, and a tree whose Compose record remains is never eligible for that sweep. A registration whose directory is already gone is cleared by that same command, so REAP never prunes repository-wide. On `<platform>` `windows-native`, WINDOWS NATIVE PROBES replaces the POSIX commands in this step.
   - For every batch merged this iteration, once its worktree is removed, delete its local head branch with `git branch -D <backlog_loop_branch>`: `--delete-branch` would have done it but cannot from a worktree, and nothing holds the branch now. Report a refusal and never retry it.
   - Everything else is reported, never killed. Repo path plus start time is not ownership. Never kill by tool name either: no `pkill -f vitest|node|go|python|pytest`.
   - On the run's final REAP, the one before FINAL REPORT or an early-stop report, and only after every run-owned worktree is removed and every Compose record is retired, delete `<worktree-root>` with `rmdir`: it is the run-owned directory recorded in `backlog_loop_worktrees`, `rmdir` refuses a directory that still holds anything, and a tree whose teardown failed keeps it. Remove nothing outside that directory, and never the invoking worktree.
   - Record `reaped: <n> group(s), <m> orphan(s)` on the batch line and list every killed command in the FINAL REPORT.

## HUMAN GATES

A human gate is work a person reserved for themselves -- an access grant, a credential, a paid subscription, a production approval, information only they hold. The loop never claims, plans, builds, or merges one, and never counts one as unfinished agent work. A backlog whose only remainder is gates has no agent work left in it; say that plainly rather than reporting it unclear.

RECOGNITION, decided in the census before anything else looks at the issue:

- The `human-gate` label, or `issue_type=gate`. Those are the only two signals. A native gate's `await_type` decides only how it is reported: `human` or absent waits on a person, while `timer`, `gh:run`, `gh:pr`, and `bead` resolve themselves.
- A title beginning `[HUMAN]` without the label is a `label-defect`: withheld from claiming exactly like a gate, reported with the label to apply, and repaired never. The prefix is a human convention that no query can rely on.
- Both labels named here -- `human-gate` and `hard-blocker` -- are author-only signals. NO step of this procedure ever writes either one, on any issue, in any mode.

Gate recognition runs BEFORE preflight's owner-decision scan, and that scan sees only issues the census classified as neither `human-gate` nor `label-defect`. The distinguishing question is not what the body sounds like but what the agent can do: an owner-decision is a preference the agent can substitute for and a human reviews in the PR; a gate is an act the agent cannot perform at all. An issue matching both is treated as a gate and reported as a labeling defect.

REPORTING. Every open human or untyped gate is named in the final report with what the person must do, taken from its description, acceptance criteria, or design field; an auto-resolving gate is named with its `await_type` and no person action. All three empty -> report it as an incomplete gate.

READ-REQUIRED references/gate-repair.md. GATE REPAIR. REPAIR, REPAIR SEQUENCE, CLEARING A QUARANTINE and REPAIRED NOTHING ELSE: how a dependency edge onto an undeclared gate is removed and its dependent quarantined. Read that file in full before running it and whenever another section names it; a run that skips the file must not perform it.

## OWNER-DECISION ISSUES

Reached only for issues CENSUS classified as neither `human-gate` nor `label-defect` -- see `## HUMAN GATES` for why that order is load-bearing. Applies to every issue whose `issue_type` is `decision`; skip none of those, whatever the body says. A body that says the loop may choose is an accepted marker from `source-to-beads`, not a requirement: a person who files a non-gate `decision` is asking for a recommendation, and the design entry, the `owner-decision` label, the PR body, and FINAL REPORT let them review it. Three classes stay with a person, and they are told apart by structure and never by reading the body: a native gate or an issue with the `human-gate` label, which CENSUS withheld before this scan; a question whose chosen option needs a credential, access grant, paid subscription, production approval, or information only a person holds, which `## HUMAN GATES` defines and a producer files as a native gate; and a decision that changes a contract, permission, or security stance or contradicts a `user-approved` decision, which `ce-plan` or the review reports, and the loop then writes `needs-person` with the question. An issue of any other type is never owner-decision, whatever its body asks. A granted decision always runs solo so one PR carries one decision. Pick your recommended option; when the issue lists no options, derive them from the issue and its design and record the rejected alternative, and when no rejected alternative can be stated, record the entry as an open area and not as a settled decision. Preserve any existing design text, append `<decision> | rejected: <alt> | reason: <why>` to the design field through a file, never a shell argument: `bd update --design` replaces the whole field, so read the current design, write it plus the appended line to a file, and run `bd update <id> --design-file <file>`. Read the field back and require the original text as an exact substring and the appended line in full; either missing -> the write did not land, so do not start the batch and report it. Add the `owner-decision` label for the user's audit. Never overwrite an existing design record.

## CONSTRAINTS

Preflight constraints hold on every diff. The applicable quality gate set is green before every PR, no exceptions. Everything written to repo, git, or tracker is English: identifiers, comments, error strings, test names, issue text, commits, PR bodies.

This procedure writes exactly four statuses: `open`, `in_progress`, `blocked`, and `closed`. It never writes `hooked`, `pinned`, or `deferred`. Those three are a person's or a sibling skill's parking decision, and CLASSIFY reads them as one. `in_progress` is written only by `bd update <id> --claim` and by ADOPTION's guarded write.

A batch member this run cannot complete is written `blocked` with a recorded `backlog_loop_cause`, plus the line `## FINAL REPORT` already requires. An open linked PR waiting on checks or mergeability uses `transient:pr-open` and OPEN PR RESUME rechecks it on later runs; a decision that truly requires a person uses `needs-person`. CLASSIFY files a `needs-person` issue as `self-blocked-needs-person`, outside the loop-responsible set; it files a recoverable open PR as `self-blocked-transient`, still in that set until its PR merges, the attempt ceiling is reached, or LINKED PR DISPOSITION sends it to `needs-person`, except that an issue whose open linked PR REPORT lists as awaiting a required approval is reported as awaiting a person and does not hold back the clear verdict. Nothing here decides whether an issue is actionable by reading its body, and nothing invents a fifth status for the case.

## STOP EARLY AND REPORT

Stop only when no legal agent-executable action remains. Before stopping, run CENSUS and distinguish a scoped issue or batch failure from a blocker that prevents every selectable issue from reaching the merge gates. A scoped plan, implementation, review, test, PR, or merge failure is written to its members with the evidence and cause required above, then the loop continues to independent `ready` work. Within one invocation an issue ID that already failed is not re-attempted; it is skipped from selection and its recorded state is reported, and a later invocation may retry it through REOPEN PASS or PROBATION PASS. The one exception is `transient:decision-recorded`, because no work failed: CENSUS may reopen it in this invocation and the issue is attempted once more, and a second `transient:decision-recorded` for the same issue in this invocation is skipped like any other failure. A second exception is `transient:scope-incomplete`, because the failure was in the scoping of `<trunk-failures>`, not in the work: it may be reselected once per invocation with the complete repair set, and a second `transient:scope-incomplete` for the same issue in this invocation is skipped like any other failure. A third exception is `transient:trunk-moved`, because the trunk changed under the batch and no work failed: it may be reselected once per invocation, from a fresh BASE, after CENSUS proves its cause gone, and a second `transient:trunk-moved` for the same issue in this invocation is skipped like any other failure. None of these exceptions relaxes the green full-gate requirement for merges or lets a repair batch drop a member. Counts of failed batches or merges never substitute for the reachability decision.

Global terminal blockers are: a REQUIRED preflight capability is absent or unauthorized; a required status check has no producer on either CI route; another live backlog-loop invocation owns state; the local default branch contains unoffered commits; required merge-queue semantics cannot be used safely; a required gate or uncovered workflow command cannot execute in the available environment; tracker enumeration or ledger recovery remains incomplete after bounded read retries; owned process or Compose cleanup cannot be proved; the machine guard remains above `2 x <cores>` after reap and recheck; or TRUNK REPAIR proves every path to green gates depends on a person, an external owner, or an external-state change the agent cannot perform. A timed-out or failed merge is terminal only when its diagnosed cause applies to every remaining batch; otherwise keep that PR open, block only its members with the PR URL retained, and continue. Name the exact human action or external change required and why no independent batch can proceed. A probe the POSIX text names that the resolved `<platform>` replaces is never an absent capability.

## FINAL REPORT

Build it from CENSUS plus the union of `bd list --all --limit 0 --metadata-field backlog_loop_run=<run-id> --json` and the same query for `backlog_loop_census=<census-run>`, plus the touched issues' notes - not from memory and not from all historical closed issues. `--metadata-field` filters on one key=value pair and repeating it narrows rather than widens, so the union is two queries and not one. Scope it to non-closed issues plus this run's own closures. A previous run's block carries a different `<run-id>` and MUST still appear. Both flags are load-bearing: `bd list` hides closed issues unless `--all` is passed and returns at most 50 rows unless `--limit 0` is. Include every decision made on the user's behalf. Report batch composition with its budget and both scoped CI observations (`batch N: <ids> | trunk CI on|off / PR CI on|off | est <n> min | actual <k> files | reaped <n>g/<m>o -> <pr url>`), every re-estimate drop and its reason, every `oversized` anchor, and every batch-level failure. For every PR-CI-off batch, name why no PR check was eligible, state explicitly that no server-side PR verification backed its merge, list the local pre- and post-merge gate set actually run, and repeat the gate-coverage gaps found in preflight. List every pending post-merge CI watch with its PR, merge SHA, first-seen time, workflow URLs, next-poll condition, and owner issue; report a red result and its repair issue or resolution proof. List every PR awaiting a required approval and every PR LINKED PR DISPOSITION sent to `needs-person`, each with its URL and reason, and every auto-merge a person armed. List every closed issue whose PR is still `OPEN` on the forge: read `bd list --all --limit 0 --status closed --has-metadata-key backlog_loop_pr --json`, drop the rows the same query with `--has-metadata-key backlog_loop_merge` returns because a recorded merge means the PR merged, deduplicate by PR URL, and read each with `gh pr view <url> --json state`. A person closed that issue, so report the issue and the URL and never close the PR. Report any externally owned in-progress issue that prevented the backlog from being declared clear. End with the UNBLOCK REPORT of the last CENSUS, verbatim, so an unattended run leaves the answer behind. List every follow-up issue FOLLOW-UP FILING created with its fingerprint and priority, every candidate it skipped as a duplicate with the issue it matched, and every candidate a cap left over. List every process the reap killed, and every runaway process it reported and deliberately left alone. After the last REAP, write `backlog_loop_heartbeat="<iso> | released"` on every member this run still holds `in_progress`, such as a `merged` member waiting on post-merge CI, so the next invocation reads it as dead at once and not after 30 minutes.
