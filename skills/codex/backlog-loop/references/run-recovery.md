# Run Recovery.

This text belongs to this skill's `SKILL.md` and is read in full before it runs.

<!-- body -->
LIVENESS, before any recovery. A marker proves an earlier run claimed the issue; it does not prove that run stopped. Read `backlog_loop_heartbeat`, whose value is `<iso> | live` or `<iso> | released`; a value with no suffix is a legacy `live`. `live` and less than 30 minutes old, or any live process carries that run's `BACKLOG_LOOP_RUN` token AND that run belongs to this repository -> another invocation is still working. A run belongs to this repository when its run-id is the `backlog_loop_run` or `backlog_loop_census` of an issue in this tracker, or when a worktree it created appears in this repository's `git worktree list`. A token found on a process of another repository's loop (the process tree's cwd is another repository, and neither test matches) is that repository's run: ignore it for LIVENESS, the census, and I8 REAP, and never signal it. The token scan reads every process on the machine, so the repository test is what keeps two projects' loops from stopping each other. `released`, a stale `live`, and an absent heartbeat are dead unless such a process exists. A process that also carries `BACKLOG_LOOP_ROLE=refresher` is a refresher, and a refresher alone does not prove a live run: it outlives a dead run by up to 6 hours. STOP and report a live run. Do not reap, reclaim, park a PR, or claim anything. On `<platform>` `windows-native`, WINDOWS NATIVE PROBES defines how this process scan reads the token and the refresher marker.

RECOVERY, by the recorded phase. Read it before touching anything.

- `merged` or `verified`: the merge is proven. For `verified`, finish the interrupted Beads close. For `merged`, inspect the durable `backlog_loop_postmerge_ci` queue entry and poll every expected workflow on the recorded merge SHA. With both recorded CI routes `on`, a missing or in-progress expected run is pending, never green, until 30 minutes have passed from the original first-seen time; then run step 7's exact-merge local gate once. If either route is `off` or missing, a missing workflow does not hold verification after the exact-merge clean-tree gate passes; an observed red workflow still enters TRUNK REPAIR. Resume I7 with the original first-seen time; never restart its 30-minute allowance on recovery. A failed run enters TRUNK REPAIR after reproducing or ruling out the failure on current trunk. When verification passes, write `verified` as I7 does, heartbeat unset in that write, add the calibration note, and `bd close` against `backlog_loop_pr`. If either recorded CI route is `off` or missing, also run the clean-tree post-merge gate at the merge SHA. A red local gate keeps the members `in_progress` at `merged` and enters TRUNK REPAIR.
- `merge-requested`: the outcome is unknown, which is exactly what this phase exists to record. Query `backlog_loop_pr` and apply LINKED PR DISPOSITION to its state; `MERGED` is the common answer and means treat as `merged` above.
- `shipping-requested`: the push and PR creation were requested but their identifiers were never recorded, so a PR may exist under a URL the ledger does not hold. Search for it by the recorded branch and head - `gh pr list --head <backlog_loop_branch> --state all --json number,url,state,headRefOid,baseRefName` - record the URL of a single match in `backlog_loop_pr`, and apply LINKED PR DISPOSITION to it. No match -> reclaim. More than one match -> the table's more-than-one-PR row: this issue alone goes to `needs-person`, and the run continues.
- `pr-open`, `built`, or `claimed`: query `backlog_loop_pr` when present; otherwise, when `backlog_loop_branch` is recorded, run the `shipping-requested` arm's branch search, because the branch is recorded at P3, before any phase past `claimed`, and a recorded branch may already carry a PR. Apply LINKED PR DISPOSITION to the PR found. No PR -> reclaim. Never resume a half-built branch into a merge; it is rebuilt.
- Absent, or any value the `backlog_loop_phase` row above does not list: an unrecognized phase is a claim about a state this procedure does not define, so the value itself is never read as a phase. Decide from the ledger's other keys instead, which record what actually happened, in this order. `backlog_loop_merge` recorded -> treat as `merged` above. Else `backlog_loop_pr` recorded -> query it and follow the `merge-requested` arm's rules. Else `backlog_loop_branch` recorded -> follow the `shipping-requested` arm's search, its scoped `needs-person` on more than one match included. Else reclaim. Name the unrecognized value, the arm taken, and the evidence key that chose it in the FINAL REPORT: an improvised value was written by something, and a recovery that swallows it leaves the next run to meet the same value with the same nothing to go on. Without this arm an unrecognized phase matches no arm at all and ends the run outright -- which is how one issue carrying one improvised value wedged every later invocation.
