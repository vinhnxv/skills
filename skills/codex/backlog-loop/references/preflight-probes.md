# Preflight Probes.

This text belongs to this skill's `SKILL.md` and is read in full before it runs.

<!-- body -->
- CI probes (REQ, non-fatal): refresh remote refs with `git fetch <remote> --prune`, resolve `<default-sha>` with `git rev-parse <remote>/<default>`, then enumerate EVERY run for that exact SHA - `gh run list --branch <default> --commit <default-sha> --limit 100 --json workflowName,conclusion,status,createdAt,headSha` - and reduce it to the latest attempt per `workflowName`. This probe determines `<trunk-ci>` health only: no run on that SHA, all matching runs concluding `startup_failure`, or a billing/quota/spending error means `<trunk-ci>=off`. A successful `main`-only workflow is **not** evidence that a PR head can receive a check. Separately inspect the exact default-branch workflow files and their enabled states for PR-capable events (`pull_request` or a `push` trigger admitting the planned head branch); `workflow_dispatch`, `merge_group`, and `pull_request_target` alone do not prove a PR-head quality check. Record a provisional `<batch-ci>` route from that evidence and any required status checks; P6 compares base and committed-head workflows, changed paths, and workflow edits, then P8 verifies the actual PR rollup. Unknown eligibility is `on` until disproved, never silent local fallback. Re-probe each current trunk SHA and each batch; CI unavailability is expected and pre-authorized, so never ask the user to fix billing.
- Merge capability (REQ): query `gh api repos/{owner}/{repo}/branches/<default>/protection`. 404 -> unprotected. A 403 is unprotected only when the response exactly says branch protection requires a paid plan or public repository; any other 403 is an authorization failure and stops. On 200 inspect `.required_status_checks`. Also query `gh api --paginate --slurp repos/{owner}/{repo}/rules/branches/<default>` and flatten all pages: applied branch rules include `required_status_checks` as well as `merge_queue`, including organization rules. A required check from either source must actually appear and pass on the PR, regardless of trunk CI; set `<batch-ci>=on` and never substitute a local gate. A required check that no default-branch workflow can produce for a pull request stops the run at preflight on either CI route, naming the check: the PR can never show it, so every PR would park on a condition only a person can change. Stop only on proven absence, read from each workflow's name, job names, and event and path filters as P6 does; a matrix or reusable-workflow job name, an undecidable enabled state, or a check pinned to a non-Actions app is an uncertain producer and never stops the run. Any `merge_queue` rule -> stop: `gh pr merge` would enqueue the PR instead of merging it, which this loop cannot verify. The rules endpoint defaults to 30 per page, so do not infer absence from the first page. This endpoint carries the SAME paid-plan carve-out as the protection query above and for the same reason The exact 403 `Upgrade to GitHub Pro or make this repository public` reads as no applicable rules here too. Any other 403, and any other response, stops. Never pass `--admin`.
- Approval requirement (REQ, non-fatal): from the protection response read `required_pull_request_reviews.required_approving_review_count` and `require_code_owner_reviews`, and from the flattened rules response read every `pull_request` rule's `required_approving_review_count` and `require_code_owner_review`; the effective requirement is the highest count from either source. Name it before the first claim as `approval required: <n> review(s) (<protection|ruleset>)`, or `approval required: none`. Never approve and never stop on it: a PR awaiting approval is LINKED PR DISPOSITION's `REVIEW_REQUIRED` row, transient and uncharged, and FINAL REPORT lists it.
- Quality gate set (REQ): read CLAUDE.md/AGENTS.md/CONTRIBUTING.md/README **at the commit being gated**, with `git show <sha>:<path>` or from inside `<clean-tree>`, never from the working tree. Re-resolve the set separately for the trunk SHA, the batch head, and the merge commit. Record every unconditional gate plus every path-conditional gate. Else use the project's test command. Do not flatten a conditional gate into one command or omit it. Record each conditional gate together with the paths that trigger it, and evaluate that trigger against each batch's actual changed files. Child verification, post-merge verification, and the final report use this same gate set.
- Gate coverage: on the first `<trunk-ci>=off` or `<batch-ci>=off` observation, read both `.github/workflows/*.yml` and `.github/workflows/*.yaml` when present. For each job applicable to the gated commit and changed paths, separate verification commands (tests, lint, type checks, builds) from runner provisioning (checkout, dependencies, caches, platform setup, artifact upload). Compare verification commands and their effective coverage against the full gate set; report each uncovered verification command. For a local-only route, run an equivalent verification gate at the committed SHA, adapting runner-specific setup to the local platform as needed. If no equivalent verification can run, block; runner provisioning alone is not an extra quality gate. Re-resolve coverage whenever a batch changes CLAUDE.md/AGENTS.md/CONTRIBUTING.md/README or anything under `.github/workflows/`.
- Process hygiene (REQ): record `<cores>` from `sysctl -n hw.ncpu`, or `nproc` where that is the platform's command. Every gate, test, build, or app command this loop runs is launched non-interactively (`CI=1`, watch and UI modes off), inside its own process group, and under a hard deadline `<gate-timeout>`, which is 20m unless the repository's CLAUDE.md, AGENTS.md, CONTRIBUTING.md, or README states a gate timeout, read at the gated commit as the quality gate set is, and then that value replaces it: `perl -e 'setpgrp(0,0); exec @ARGV' -- timeout -k 30s <gate-timeout> <command>`. `timeout` is `gtimeout` from Homebrew coreutils on macOS; where neither exists, keep the process group and enforce the deadline by killing that group. `<gate-timeout-cap>` is 60m. A DEADLINE is a wrapper exit status of 124 or 137 whose elapsed time is at or above `<gate-timeout>` minus 5 seconds; any other non-zero status is the command's own failure. Export `BACKLOG_LOOP_RUN=<run-id>` into the host session environment right after choosing `<run-id>` and before any child skill runs, so every command a child launches -- `ce-work` tests, the `ce-test-browser` dev server, `ce-babysit-pr`, `ce-debug` -- carries the token a REAP or a dead-run sweep finds it by. Every child brief restates the hygiene rules in one sentence: run every gate, test, build, or app command non-interactively (`CI=1`, watch and UI modes off), never leave a watcher, dev server, or REPL alive past the command that needed it, and never signal a process you did not start. Append every launched leader PID to `<owned-pgids>`, the set the I1 machine guard resets each iteration.
