# Gate Repair.

This text belongs to this skill's `SKILL.md` and is read in full before it runs.

<!-- body -->
REPAIR. The repository convention this procedure serves says a gate must not be a dependency of other work, and that any real exception is declared explicitly. So a gate holding another issue with no declaration contradicts its own recorded intent. That, and only that, is repairable here.

- The declaration is the `hard-blocker` label on the gate. Free prose is never read as one, however clearly it is written.
- ADOPTION GATE, evaluated first, every run. When NO issue anywhere in the tracker carries a `hard-blocker` label, the repository has not adopted the convention: report every undeclared gate edge with the exact label to apply, and remove none of them. The first `hard-blocker` anywhere is the operator's adoption of the convention; after it exists, the rule below applies normally.
- A native gate (`issue_type=gate`) is NEVER repaired or quarantined: its blocking edge is declared by construction, so every edge a producer such as `source-to-beads` writes on one stands. `bd create --type gate` and `bd gate create --blocks <id>` are how it comes into being, and no label is needed to declare it, so a native gate that also carries `human-gate` is still exempt and no `hard-blocker` is ever required of its producer. Report it and leave it, and never quarantine the issue it holds. Only a label-identified gate is ever repaired.
- `<repair-ceiling>=5` edge removals per run. Reaching it stops the pass and reports the remainder rather than working through a whole tracker unattended in one pass.

REPAIR SEQUENCE, per undeclared edge, in this order. Everything that must survive a crash is written BEFORE the destructive step, the quarantine included:

1. Write the removal record on the gate, in TWO parts:
   - The record itself goes in a note: `bd update <gate-id> --append-notes="edge removed: <gate-id> blocks <dep-id> | <edge-type> | census <census-run> | <iso-time> | labels observed: <labels>"`.
   - The index goes in metadata: read the gate's current `backlog_loop_edge_removed`, append `<dep-id>` to that space-separated list, and write the whole value back. `--set-metadata` REPLACES a value. The list is what sequence item 2's skip test reads.
2. Read the gate's acceptance criteria, append the release condition to what is already there, and write the whole field back. `bd update --acceptance` REPLACES, there is no append form, and unlike description and design there is no `--acceptance-file` either, so the entire field round-trips through one shell argument. Then re-read it and require BOTH: the release condition present in full, and the author's original text still present as an exact substring. Either half missing -> the write did not land: stop this repair, restore nothing else, and report it. Never proceed to the removal on an unverified acceptance write. Skip items 1 and 2 entirely when `<dep-id>` is already in the gate's `backlog_loop_edge_removed` list and the release condition is already in its acceptance; a second run must not duplicate either.
3. Write the same note on the dependent, and append `<gate-id>` to ITS `backlog_loop_edge_removed` list the same way.
4. Quarantine the dependent: `bd update <dep-id> --set-metadata backlog_loop_quarantine="census <census-run> | <iso-time>"`. A quarantined issue is never admitted to a batch, by any run, and CENSUS files it under its own category so it leaves the loop-responsible set entirely.
5. `bd dep remove <dep-id> <gate-id>` -- the DEPENDENT first, then what it depends on. That order is not a style choice and getting it wrong is not an error: `bd dep remove <gate-id> <dep-id>` exits 0 and prints `Removed dependency: <gate> no longer depends on <dep>` while the real edge stays exactly where it was. After the command, RE-READ the dependent's `dependencies` array and require `<gate-id>` to be gone; report the repair only on that read-back, never on the command's exit status. This is the irreversible step and it is deliberately last. Re-read the gate's labels immediately before it and abandon this repair if a `hard-blocker` has appeared since enumeration.

CLEARING A QUARANTINE. The operator clears `backlog_loop_quarantine` by hand, or this procedure clears it when the removal has been acknowledged -- meaning the gate's `backlog_loop_edge_ack` metadata holds a space-separated list of dependent ids that includes this one. Nothing in this procedure ever writes that key; like `hard-blocker` it is author-only. Report the exact key and the exact value to append beside every quarantined issue, so the person is never left guessing what "acknowledge" means.

REPAIRED NOTHING ELSE. Every other census finding is reported and left alone -- a gate nested as a child step inside an implementation epic, a gate whose label and title prefix disagree, a dependency cycle, a gate carrying `hard-blocker` and holding work. A declared gate's edge stays, and the report names the declaration as the reason the dependent cannot start. The run can show it changed nothing outside the repairs it reported, labels included.
